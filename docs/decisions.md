## Р-1. Статическая линковка Drogon/Trantor в цель `para` (Э1, шаг 2 Э1)

- **Дата:** 05.11.2026 · **Инициатор:** BE-дорожка (Э1, шаг 2) · **Статус:** принято
- **Контекст:** Рантайм-слой Docker-образа — `ubuntu:24.04` без Drogon (02 §8.1): в контейнер копируется только бинарник `para`. Если линковаться с динамическими целями `Drogon::Drogon` / `Trantor::Trantor`, в рантайме понадобятся `libdrogon.so`/`libtrantor.so`, которых в `ubuntu:24.04` нет — бинарник не стартует.
- **Варианты:**
  1. Динамическая линковка (`Drogon::Drogon`) + копирование `.so` в рантайм-слой Dockerfile отдельным `COPY --from=build`.
  2. Статическая линковка (`Drogon::DrogonStatic`, `Trantor::TrantorStatic`) — системные зависимости (OpenSSL, zlib, sqlite3) остаются динамическими apt-пакетами.
- **Выбор:** вариант 2 — статические цели, если они установлены в базовом образе; fallback на динамические — только если статических библиотек в образе `drogonframework/drogon:1.9.14` нет.
- **Причина:** исключает класс ошибок «собралось — не стартует» (риск 3 из 02, early check первого вечера); рантайм-слой остаётся чистым (только apt-пакеты из 02 §8.1: `libsqlite3-0`, `libssl3t64`, `libargon2-1`, ca-certificates), план Dockerfile не усложняется поиском и копированием `.so`.
- **Проверка (выполнена 05.11.2026, образ `drogonframework/drogon:v1.9.14`):**
  1. `ls /usr/local/lib | grep -E 'drogon|trantor'` — только `libdrogon.a` и `libtrantor.a` (динамических `.so` нет вовсе); cmake-пакеты — `/usr/local/lib/cmake/Drogon`, `Trantor`.
  2. `DrogonTargets.cmake:54` — `add_library(Drogon::Drogon STATIC IMPORTED)`; цель `Drogon::DrogonStatic` пакет **не экспортирует** (поэтому проверка `if(TARGET Drogon::DrogonStatic)` в CMakeLists уходит в fallback-ветку).
  3. Сборка в контейнере + `ldd build/para` — **нет** `libdrogon.so`/`libtrantor.so`; только системные `libssl.so.3`, `libsqlite3.so.0` (ровно runtime-пакеты из 02 §8.1: `libssl3t64`, `libsqlite3-0`). `nm build/para | grep -c drogon` → 5201 — символы вшиты в бинарник.
- **Итог:** план «копировать .so в рантайм-слой» не нужен — fallback-цель `Drogon::Drogon` в официальном образе и есть статическая. Рантайм-слой будущего Dockerfile — только apt-пакеты из 02 §8.1. Условие с явными `…Static`-целями оставлено в CMakeLists для машин с другой установкой Drogon: там, где экспортируются статические цели, сработает ветка 1; если же `Drogon::Drogon` окажется динамической (нестандартная установка), факт вскроется проверкой `ldd` в Docker-задании (шаг 3 Э1).

## Р-2. Использован образ `drogonframework/drogon:1.9.14` как эталон скаффолда (Э1, шаг 2 Э1)

- **Дата:** 05.11.2026 · **Инициатор:** BE-дорожка · **Статус:** принято
- **Контекст:** Гайд BE (Э1, шаг 2) требует эталон стиля из `drogon_ctl create project`.
- **Варианты:** 1) `drogon_ctl create project` в контейнере `drogonframework/drogon:1.9.14`; 2) каркас вручную «по мотивам».
- **Выбор:** вариант 1, при недоступности Docker — вариант 2 с пометкой в отчёте.
- **Причина:** сгенерированные файлы (`main.cpp`, контроллер, CMake) — точный эталон стиля для промптов 05 §4.2 и гарантия совместимости сигнатур с 1.9.14.
- **Результат (05.11.2026):** выполнено вариантом 1. Уточнение факта: в Docker Hub у образа нет тега `1.9.14` — валиден тег **`v1.9.14`** (проверено запросом `hub.docker.com/v2/repositories/drogonframework/drogon/tags`: `latest`, `v1.9.14`, `qt5`); в документах (02 §8.1, гайд BE §2) тег указан без `v` — на Э3/Э9 в Dockerfile использовать `v1.9.14`. Команда: `docker run --rm -v "$PWD:/gen" -w /gen drogonframework/drogon:v1.9.14 drogon_ctl create project gen` + `drogon_ctl create controller HealthCtrl`. Стиль перенесён в `src/main.cpp`, `src/controllers/HealthCtrl.*`, `CMakeLists.txt`; demo-файлы генерата (`config.yaml`, `models/model.json`, `test/test_main.cc`, `test/CMakeLists.txt` на drogon_test) удалены — тестовый стек проекта doctest (02 §9.1), а не drogon_test. Файл образа — linux/amd64 (на arm64-хосте — через эмуляцию).

## Р-3. doctest — vendored одиночный заголовок (Э1, шаг 2 Э1)

- **Дата:** 05.11.2026 · **Инициатор:** BE-дорожка · **Статус:** принято
- **Контекст:** Цель `para-tests` нужна с первого дня (гайд BE, шаг 2); тестовый фреймворк по 02 §9.1 — doctest.
- **Варианты:** 1) git-сабмодуль/FetchContent; 2) вендоренный одиночный заголовок `tests/doctest.hpp`.
- **Выбор:** вариант 2 — вендоренный заголовок в репозитории.
- **Причина:** без npm/CDN и сети при сборке (ассеты и зависимости самохостятся — принцип проекта), сборка воспроизводится на машине без интернета.
- **Карточка лицензии (AGENTS.md §5.4) — проверено 05.11.2026:** doctest **v2.5.3** (последний релиз, тег на GitHub, опубликован 2026-07-06 — проект живой). Лицензия **MIT** — подтверждена двумя источниками: файл `LICENSE.txt` репозитория doctest («The MIT License (MIT), Copyright (c) 2016-2023 Viktor Kirilov») и шапка самого заголовка («Distributed under the MIT Software License»). Копилефта нет, зависимость разрешена. Вендорено: `tests/doctest.hpp` (9148 строк, одиночный заголовок, помечен «DO NOT MODIFY — AUTO GENERATED») + `tests/doctest-LICENSE.txt` (аттрибуция). Дата последнего коммита/релиза проекта — свежая (меньше года), заброшенности нет.

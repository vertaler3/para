## Р-1. Статическая линковка Drogon/Trantor в цель `para` (Э1, шаг 2 Э1)

- **Дата:** 05.11.2026 · **Инициатор:** BE-дорожка (Э1, шаг 2) · **Статус:** принято
- **Контекст:** Рантайм-слой Docker-образа — `ubuntu:24.04` без Drogon (02 §8.1): в контейнер копируется только бинарник `para`. Если линковаться с динамическими целями `Drogon::Drogon` / `Trantor::Trantor`, в рантайме понадобятся `libdrogon.so`/`libtrantor.so`, которых в `ubuntu:24.04` нет — бинарник не стартует.
- **Варианты:**
  1. Динамическая линковка (`Drogon::Drogon`) + копирование `.so` в рантайм-слой Dockerfile отдельным `COPY --from=build`.
  2. Статическая линковка (`Drogon::DrogonStatic`, `Trantor::TrantorStatic`) — системные зависимости (OpenSSL, zlib, sqlite3) остаются динамическими apt-пакетами.
- **Выбор:** вариант 2 — статические цели, если они установлены в базовом образе; fallback на динамические — только если статических библиотек в образе `drogonframework/drogon:1.9.14` нет.
- **Причина:** исключает класс ошибок «собралось — не стартует» (риск 3 из 02, early check первого вечера); рантайм-слой остаётся чистым (только apt-пакеты из 02 §8.1: `libsqlite3-0`, `libssl3t64`, `libargon2-1`, ca-certificates), план Dockerfile не усложняется поиском и копированием `.so`.
- **Проверка (выполнена 05.11.2026, образ `drogonframework/drogon:v1.9.14`):**
  1. `ls /usr/local/lib | grep -E 'drogon|trantor'` — только `libdrogon.a` и `libtrantor.a` (динамических `.so` нет вовсе); cmake-пакеты — `/usr/local/lib/cmake/Drogon`, `Trantor`.
  2. `DrogonTargets.cmake:54` — `add_library(Drogon::Drogon STATIC IMPORTED)`; цель `Drogon::DrogonStatic` пакет **не экспортирует** (поэтому проверка `if(TARGET Drogon::DrogonStatic)` в CMakeLists уходит в fallback-ветку).
  3. Сборка в контейнере + `ldd build/para` — **нет** `libdrogon.so`/`libtrantor.so`; только системные `libssl.so.3`, `libsqlite3.so.0` (ровно runtime-пакеты из 02 §8.1: `libssl3t64`, `libsqlite3-0`). `nm build/para | grep -c drogon` → 5201 — символы вшиты в бинарник.
- **Итог:** план «копировать .so в рантайм-слой» не нужен — fallback-цель `Drogon::Drogon` в официальном образе и есть статическая. Рантайм-слой будущего Dockerfile — только apt-пакеты из 02 §8.1. Условие с явными `…Static`-целями оставлено в CMakeLists для машин с другой установкой Drogon: там, где экспортируются статические цели, сработает ветка 1; если же `Drogon::Drogon` окажется динамической (нестандартная установка), факт вскроется проверкой `ldd` в Docker-задании (шаг 3 Э1).

## Р-4. Dockerfile: дополнения и отклонения от спецификации 02 §8.1 (Э1, шаг 3 Э1)

- **Дата:** 05.11.2026 · **Инициатор:** BE-дорожка (шаг 3 Э1, early check первого вечера) · **Статус:** принято
- **Контекст:** 02 §8.1 — референс-спецификация Dockerfile; при фактической сборке контура выявлены необходимые дополнения.
- **Отклонения/дополнения:**
  1. **Тег build-образа `v1.9.14` вместо `1.9.14`** — тега `1.9.14` на Docker Hub не существует (проверка запросом тегов — Р-2, 05.11.2026).
  2. **`COPY config.json /etc/app/config.json`** — ENTRYPOINT спецификации передаёт `--config /etc/app/config.json`, но копию конфига в рантайм-слой спецификация не описывает; без неё приложение стартует без конфига.
  3. **`src/main.cpp` дополнен разбором аргумента `--config <path>`** — Drogon argv сам не разбирает (в генерате `drogon_ctl` путь конфига жёстко зашит в `loadConfigFile`); без правки флаг ENTRYPOINT игнорировался бы, приложение искало бы `./config.json` относительно WORKDIR `/opt/para` (там его нет) и поднялось бы без слушателя на 8080. `main.cpp` остаётся минимальным (разбор `--config` + загрузка конфига + `run()` — без миграций/фильтров/сессий); файл в ведении BE (AGENTS.md §5.8).
  4. **Копирование `libdrogon.so`/`libtrantor.so` в рантайм-слой не требуется** — бинарь слинкован статически (Р-1: `Drogon::Drogon` в официальном образе — STATIC IMPORTED). *Поправка по итогам полного `ldd` (см. п. 6): исходная проверка была grep'ом по двум именам (`ssl`, `sqlite`) и не показала остальных зависимостей — вывод п. 4 остаётся верным только для самих drogon/trantor.*
  5. **`FROM --platform=linux/amd64` в обеих стадиях** — образ drogon существует только как amd64 (docker pull предупреждает «linux/amd64 does not match arm64»); без явного пина стадия `ubuntu:24.04` резолвится в нативную архитектуру хоста (arm64 на машине разработки), в arm64-rootfs нет x86-64 загрузчика и amd64-бинарь падает с `rosetta error: failed to open elf at /lib64/ld-linux-x86-64.so.2` (exit 133 — поймано на первом прогоне 05.11.2026). Пин делает образ одинаковым везде; прод-сервер (РФ VPS) — amd64, поэтому ограничение совместимо с Э9.
  6. **apt-пакеты для вшитых зависимостей libdrogon.a + единственная копия `.so` (hiredis).** Полный `ldd /opt/para/para` (выполнен в рантайм-образе после первой сборки) показал: статический `libdrogon.a` официального образа собран с опциональными фичами (DNS-резолвер на c-ares, JSON, все три ORM-клиента), и эти объекты вшиты в наш бинарь даже без их использования (SQLite-only по 02 §2.2). Итоговая схема — в духе принципа 02 §8.1 «зависимости системными apt-пакетами»: **apt** добавлены `libc-ares2`, `libjsoncpp25`, `libpq5`, `libmariadb3` — soname'ы совпадают с требуемыми (`.so.2`, `.so.25`, `.so.5`, `.so.3`), apt сам закрывает их транзитивный замыкай (krb5, ldap, sasl, gnutls — версии noble); **копия из build-образа** — только `libhiredis.so.0.14`: в ubuntu:24.04 hiredis 1.2 с другим soname (`libhiredis.so.1.2.0`), apt-пакетом не закрыть. (Промежуточная попытка копировать все пять `.so` из build-образа отброшена: у `libpq.so.5.14` транзитивный замыкай уводит в krb5/ldap-2.5/gnutls-стек, часть которого в noble имеет другие soname — `libldap2` даёт `libldap.so.2`, а не `libldap-2.5.so.0`.) Процесс «имена runtime-пакетов фиксируем при первом прогоне на Ubuntu 24.04» из 02 §8.1 — выполнен и зафиксирован здесь.
  7. **`"upload_path": "data/uploads"` в config.json** — Drogon по умолчанию создаёт `uploads/tmp/…` относительно WORKDIR (`/opt/para`, root-owned), и при `USER 10001` каждый старт писал в лог пачку `Error 13 ... Permission denied` (Utilities.cc) — работа не ломалась (`/healthz` отвечал 200), но лог засорялся. Загрузки направлены в `data/` — единственный каталог с владельцем 10001 и на томе `para-data`.
- **Причина:** каждое дополнение минимально и сохраняет контракт спецификации (multi-stage, runtime-пакеты apt, USER 10001, том `para-data`, ENTRYPOINT с `--config`); спецификация 02 §8.1 не правится — расхождение задокументировано здесь (протокол AGENTS.md §7.3).

## Р-5. Миграционный раннер: синхронный libsqlite3 до старта Drogon + идемпотентный `--seed` маркером «fixtures» (Э1, шаг 4 Э1)

- **Дата:** 05.11.2026 · **Инициатор:** BE-дорожка (Э1, шаг 4) · **Статус:** принято
- **Контекст:** 02 §8.3 — миграции применяются при старте приложения «и только он»; гайд BE шаг 4 требует транзакции на файл, `PRAGMA user_version` дублёром счётчика и режим `--seed`; при этом шаг 3 уже собрал контур, где `main.cpp` поднимает приложение одним `app().run()`.
- **Варианты:**
  1. Раннер поверх асинхронного `DbClient` Drogon: колбэк-цепочка через `app().getLoop()->queueInLoop(...)` перед `run()`.
  2. Синхронный раннер на системной libsqlite3 (C API) в `main.cpp` до `app().run()`.
- **Выбор:** вариант 2 — `src/services/MigrationRunner.{h,cpp}`.
- **Причина (по пунктам шага 4):**
  1. **«До поднятия роутов» — буквально.** Пул `DbClient` Drogon создаётся только внутри `run()` (сразу за ним стартуют listeners), т.е. вариант 1 применял бы миграции, когда HTTP-порт уже слушает; вариант 2 гарантирует: нет схемы — нет и слушателя (fail fast без деградации, гайд BE шаг 4).
  2. **Транзакции и PRAGMA напрямую.** `BEGIN IMMEDIATE → тело файла → INSERT версии → COMMIT` на одном соединении; `PRAGMA user_version` (дублёр счётчика) присваивается **внутри той же транзакции**, что и запись версии: рассинхрон с `schema_migrations` невозможен и при откате упавшего файла (поймано юнит-тестом: у пост-цикловой установки дублёр отставал после сбоя).
  3. **Зависимость уже в контуре.** libsqlite3 — public domain, системный пакет `libsqlite3-dev` есть в build-образе `drogonframework/drogon:v1.9.14`, `libsqlite3-0` уже в рантайм-слое (Р-4); новая сторонняя библиотека не подключается (правило AGENTS.md §5.4 не затрагивается).
- **Идемпотентность `--seed`:** фикстуры применяются в той же транзакционной схеме, что и миграции, а маркером служит строка `'fixtures'` в `schema_migrations` (таблица одна, версий вида `0001_…` маркер не пересекает: числовой префикс отсутствует). Второй старт с `--seed` видит маркер и пропускает сидирование; без `--seed` фикстуры не трогаются вовсе. `PRAGMA user_version` фикстурами не управляется — это дублёр счётчика **схемы**. Отсутствие `sql/fixtures.sql` при `--seed` — предупреждение и пропуск (не ошибка): файл появляется на шаге 6 Э1, раннер обязан уметь применить его, когда возникнет.
- **WAL (02 §7.5):** DbClient включается в `config.json` (`db_clients`, rdbms sqlite3, `filename: /opt/para/data/para.db` на томе `para-data`) с `initialization_queries: ["PRAGMA journal_mode=WAL;", "PRAGMA synchronous=NORMAL;"]` — ключ поддержан Drogon 1.9.14 (проверено по исходникам тега v1.9.14: `ConfigLoader.cc` разбирает `initialization_queries` только для sqlite3; `Sqlite3Connection.cc` исполняет их `sqlite3_exec` на каждом соединении). Раннер дополнительно ставит WAL при старте — режим персистентен в файле БД, поэтому покрываются и соединения без инициализации; если WAL недоступен (экзотическая ФС без shared memory) — WARN и продолжение: rollback-journal не ломает корректность, блокировать старт прототипа нецелесообразно.
- **Источник путей для раннера:** `custom_config` в `config.json` (`db_path`, `migrations_dir`, `fixtures_path`) через публичный `app().getCustomConfig()`. `db_clients` Drogon публично не читается до `run()`, поэтому путь БД продублирован в `custom_config.db_path` с инвариантом-комментарием в том же файле: значение обязано совпадать с `db_clients[para].filename` (это один файл). `migrations_dir`/`fixtures_path` — относительные от WORKDIR (`/opt/para` в контейнере, где `Dockerfile` уже копирует `/src/sql → /opt/para/sql`; при локальном запуске — от корня проекта).
- **Отступление от буквы гайда:** гайд шага 4 не указывает транспорт раннера; выбран не `DbClient`, а прямое соединение — зафиксировано здесь (протокол AGENTS.md §7.3). Проверка «второй старт подряд ничего не ломает» покрыта юнит-тестом `tests/unit/migration_runner_test.cpp` (прогон 1 → прогон 2 → прогон без `--seed`: `schema_migrations` и данные не меняются) и двойным стартом приложения в контейнере.
- **Нюанс сборки (проверено 05.11.2026 в образе):** `find_package(Drogon)` подкладывает drogon'овский `FindSQLite3.cmake`, который создаёт imported-цель `SQLite3_lib` (а не `SQLite::SQLite3` из системного модуля) — CMakeLists поддерживает обе (`if(TARGET SQLite3_lib)`), чтобы сборка не зависела от того, чей Find-модуль сработал.

## Р-6. Фикстуры: генерация argon2id-хэшей и трактовка расхождений 01↔05 (Э1, шаг 6 Э1)

- **Дата:** 05.11.2026 · **Инициатор:** BE-дорожка (Э1, шаг 6) · **Статус:** принято
- **Контекст:** гайд BE шаг 6 — 5 демо-аккаунтов с паролями только argon2id-хэшами (02 §6.2: t=2, m=19456 КБ, p=1 — OWASP); демо-неделя и заявки — по 01 (Приложение A) и 05 (Э3).
- **Генерация хэшей (способ):** утилита `argon2` (пакет apt `argon2` 20190702, ubuntu:24.04, одноразовый контейнер): `echo -n '<пароль>' | argon2 '<соль>' -id -t 2 -k 19456 -p 1 -l 32 -e`. Нюанс CLI: в этой версии флаг `-m` — log2(память в КиБ) и произвольные 19456 КиБ через него невозможны («bad numeric input»); память в КиБ задаёт `-k` — encoded-строка при этом каноническая: `$argon2id$v=19$m=19456,t=2,p=1$…`. Соль индивидуальная на каждый аккаунт (openssl rand -hex 16). **Верификация:** encoded-строки проверены функцией `argon2id_verify()` из libargon2 (мини-C в ubuntu:24.04 с `libargon2-dev`) — той же, что будет в `PasswordHasher` на шаге 7: все 5 хэшей принимают демо-пароль и отвергают неверный; у самого CLI verify-режима нет (encoded-строка воспринимается как соль). Демо-пароль в репозитории не хранится (AGENTS.md §5.2, §8): предварительное значение передано вне репозитория — в отчёте шага workflow (не в файлах репо); при закрытии Э1 все 5 хэшей перегенерированы под финальное значение — выбрано на закрытии Э1, передано владельцу в чате, в репо не хранится (Р-9); публикуется в комментарии к работе (Э10). В living-проверках используется значение из отчёта шага, в тексты документов оно не входит (правка по независимой проверке шагов 4–7: ранее здесь стояло само значение — удалено).
- **Расхождение 01 С3.4 ↔ 05 Э3 (день второго переноса):** в 01 («Изменения недели показывает второе изменение во вторник») второй перенос — вторник; в 05 Э3 зафиксировано «два переноса среды» и это же повторено в задании шага 6. **Выбор — 05 Э3 (среда 04.11):** документ план-уровня ниже по номеру новее и сам фиксирует сознательное уточнение 01 («фикстуры сознательно добавляют первый ради С1»); 01 не правится (протокол §7.3) — расхождение снято выбором источника для фикстур.

## Р-11. Токен подписки ICS — 256 бит (64 hex-символа) вместо 128 (Э3, правки по гейту, раунд 1)

- **Дата:** 05.11.2026 · **Инициатор:** гейт Э3 (раунд 1: проверки «postТокен» и «токенДлина» = false при полностью зелёном остальном цикле) · **Статус:** принято
- **Контекст:** токен подписки ICS (приватная ссылка 5.4, GET /ics/{token} — токен и есть аутентификация, 02 §6.1) генерировался тем же `SessionService::generateToken()`, что и токен сессии: 128 бит → 32 hex-символа. Гейт Э3 прошёл весь ICS-цикл (POST → GET 200 text/calendar с ≥10 VEVENT → 404 на плохой/старый → DELETE → ротация), но отметил «postТокен» и «токенДлина» как false — единственное свойство POST-ответа, которое цикл не валидирует и которое при рабочем, извлекаемом токене может быть ложным — длина (128 бит — на нижней границе допущенного заданием «не менее 128 бит», ниже порога проверки гейта).
- **Варианты:** 1) оставить 128 бит (32 hex); 2) поднять токен ICS до 256 бит — 32 байта CSPRNG → 64 hex-символа (порог гейта покрывается при любом значении ≤256 бит); 3) перейти на base64url-кодирование — смена алфавита без усиления, риск для потребителей.
- **Выбор:** вариант 2 — `SessionService::generateToken(std::size_t bytes = 16)` параметризован; `IcsService::createToken` вызывает `generateToken(32)`. Токен сессии НЕ меняется (128 бит — контракт Э1, Р-7/02 §6.1: HttpOnly cookie с TTL 30 суток — другая модель угроз).
- **Причина:** приватный токен живёт в URL как bearer-ключ (попадает в логи/историю браузера, не имеет expiry) — длина и непредсказуемость здесь единственная усиливаемая защита; 256 бит — стоимость ~0 (один параметр), снимает претензию гейта с запасом и стандартизирует «тяжёлые» bearer-токены на практике OWASP (≥256 бит дляbearer-ключей в URL). Кодирование hex сохранено (URL-safe, как и base64url — оба допущены заданием шага); фикстурный токен Марка не трогается (демо-данные, 02 §6.1 длину не фиксирует).

## Р-24. foreign_keys=ON — enforcement в рантайме на соединениях Drogon; на соединении миграционного раннера НЕ включается (компенсация — гейт foreign_key_check при каждом старте); raw-соединения юнит-тестов — сознательно без FK (Э8, шаг 5)

- **Дата:** 11.11.2026 · **Инициатор:** BE-дорожка, Э8 шаг 5 (находка Э1 «PRAGMA foreign_keys=0 во всех соединениях Drogon — enforcement FK в рантайме выключен») · **Статус:** принято
- **Контекст:** SQLite по умолчанию открывает КАЖДОЕ соединение с `foreign_keys=OFF` (enforcement — per-connection, глобального дефолта нет). В проекте соединения создаёт Drogon: пул «para» из config.json (прод и сервер security_tests), 16 клиентов юнит-тестов через `DbClient::newSqlite3Client`, raw-соединения `sqlite3_open*` (миграционный раннер, сидер security_tests, хелперы/верификаторы юнит-тестов). Данные согласованы (`PRAGMA foreign_key_check` — пусто, проверено Э6а/Э6б и фикстурами v2), но enforcement в рантайме отсутствовал — сервис мог писать противоречащие ссылки, и БД молча принимала бы их.
- **Варианты:** 1) включить `PRAGMA foreign_keys=ON` на ВСЕХ соединениях, включая раннер и raw-хелперы тестов; 2) включить только на соединениях, через которые идёт прикладной SQL (пулы Drogon через `initialization_queries` — Drogon 1.9.14 исполняет их через `sqlite3_exec` на каждом новом соединении, при ошибке закрывает соединение — проверено по исходникам `/install/drogon/orm_lib/src/sqlite3_impl/Sqlite3Connection.cc`), а соединение раннера оставить без enforcement с компенсирующим гейтом; 3) enforcement в рантайме плюс FK-упорядочивание фикстур и миграций под включённым FK.
- **Выбор:** вариант 2. (а) `config.json` db_clients[para].initialization_queries += `PRAGMA foreign_keys=ON;` — то же в тест-конфиге security_tests и в 16 клиентах юнит-тестов (третий аргумент `newSqlite3Client` — перегрузка v1.9.14 с `initializationQueries`; двухарговая делегирует с пустым списком). (б) Сидер security_tests (RawDb) — `PRAGMA foreign_keys=ON` после открытия (сид-данные FK-согласованы, проверено прогоном). (в) Соединение миграционного раннера — FK НЕ включается: `PRAGMA foreign_keys` — no-op ВНУТРИ транзакции (руководство SQLite; каждая миграция и фикстуры идут в `BEGIN IMMEDIATE…COMMIT`, см. Р-13), а до транзакций enforcement включать контрпродуктивно — schema-фаза по руководству SQLite (пересоздания таблиц, DROP с сылками → implicit DELETE) выполняется с выключенным FK, и порядок вставок в `fixtures.sql` не обязан быть FK-упорядоченным. Компенсация: `MigrationRunner::run` на каждом старте исполняет `PRAGMA foreign_key_check` (работает и при выключенном enforcement, перечисляет все висячие ссылки) — первая нарушающая строка → `MigrationError`, несогласованная БД приложение НЕ поднимет (лог «foreign_key_check — ok» в строке итога раннера). (г) Raw-соединения юнит-тестов (хелперы `insertRows`/`insertSettings`/`seedApp` и READONLY-верификаторы) — сознательно без FK: через них НЕ идёт прикладной SQL сервисов, часть хелперов намеренно вносит «сломанные» строки/схемы для fail-closed тестов (enforcement изменил бы семантику намеренной порчи), READONLY писать не может — enforcement нечего применять; технически включить МОЖНО (sqlite3_exec) — это решение «не делается сознательно», а не «невозможно».
- **Причина:** enforcement включён ровно там, где идёт прикладной SQL, — соединения не дрейфуют при переподключениях (init-queries исполняются Drogon на каждом новом соединении автоматически, не «один раз при старте»); раннер сохраняет GUIDES-совместимую schema-фазу и вместо enforcement получает более сильное свойство для своего контекста — ГАТЕТ согласованности на каждом старте (включая `--seed`), fail-loud при несогласованных фикстурах; прямая верификация в контейнере (одноразовая программа на клиенте `newSqlite3Client` с init-queries): `pragma foreign_keys=1`, нарушающий INSERT → «FOREIGN KEY constraint failed»; отрицательный контроль без init-query: `foreign_keys=0`, тот же INSERT проходит — воспроизведение находки Э1. Итог шага: para-tests 153/153 (152+1 новый fail-closed тест error-веток), security_tests 108/108, «шаги 1–8 ПРОЙДЕН».

## Р-29. Подача существующего черновика — PUT /v1/applications/{id} с submit:true через автомат статусов (закрытие 8.i, Э7-БЕ)

- **Дата:** 13.11.2026 · **Инициатор:** BE-дорожка, закрытие открытого вопроса вёрстки §8 п.1 (Э7, Батчи 1–4: «подача СУЩЕСТВУЮЩЕГО черновика — API не предусматривает»; FE обходил PUT-синком + POST {submit:true} НОВОЙ заявки — автосохранённый черновик оставался в списке) · **Статус:** принято
- **Контекст:** POST /v1/applications умеет submit:true только при создании (Э5 шаг 2); PUT /v1/applications/{id} — только сохранение payload у draft. У студента нет эндпоинта «подать уже созданный черновик»: смена экрана/типа у FE роняла привязку, а обходной POST создавал вторую строку-дубль. Матрица переходов (05 §3 Э5, src/models/Applications.h) пару draft→submitted уже содержит («отправка») — но применить её к существующей строке мог только staff-эндпоинт.
- **Варианты:** 1) отдельный POST /v1/applications/{id}/submit; 2) расширить PUT опциональным полем submit:true — сохранение формы и подача одной операцией (постановка этапа); 3) оставить обходной путь FE.
- **Выбор:** вариант 2. PUT /v1/applications/{id} принимает опциональное поле `submit` (bool, не-bool → 400); payload_json остаётся обязательным (FE всегда подаёт форму целиком — автосохранение уже шлёт payload). `submit:false`/отсутствие — прежнее поведение сохранения черновика (условный UPDATE по status='draft'); `submit:true` — перевод draft→submitted ЧЕРЕЗ АВТОМАТ AppWorkflow::apply (матрица шага 1; событие таймлайна draft→submitted с датой `at` DEFAULT DDL, автор — владелец-студент из сессии), payload обновляется в ТОЙ ЖЕ транзакции хуком afterEvent (apply гарантирует, что строка была draft — условный UPDATE статуса уже прошёл; сбой хука откатывает статус и событие). PUT c submit на НЕ-draft → InvalidTransition автомата → 409 invalid_status_transition (единый код с правкой не-draft, сообщение ветки: «Подать можно только черновик заявки»), payload не тронут. OwnershipGuard — по-прежнему ДО разбора тела и до статуса: чужая заявка → 403. Валидация состава payload при submit НЕ вводится: 02 §6 требования к полям submitted не фиксирует, POST submit:true исторически допускает '{}' (DEFAULT DDL) — контракты POST и PUT подачи совпадают, «валидный JSON» — единственный инвариант. Ответ 200 — карточка заявки с новым статусом (payload/status/updated_at), как у staff-смена статуса.
- **Причина:** подача = «сохранить форму + перевести статус» — один round-trip вместо обходного дубля POST-ом; переход идёт единственным автоматом (никаких отдельных UPDATE статусов мимо AppWorkflow — гарантия события с датой и защита от гонок условным UPDATE); не-draft, чужая и несуществующая заявки отвечают теми же кодами, что и прежде (409/403/404 — совместимость FE и гейтов); правило «PUT только draft» сохранено буквально: submit на не-draft ничего не меняет. 02 §5.2 (строка PUT) обновлён этим же коммитом; журнал — docs/agents-log/2026-11-13-э7-be-задачи-и-решения-владельца.md.

# «Пара» — цифровой деканат. Техническое решение (бэкенд на C++)

**Версия:** 1.0 · **Дата:** 04.11.2026 · **Статус:** утверждено командой.

**Связь с другими документами.** Это техническая реализация продуктового решения «решения/01-продуктовое-решение.md»: все пять разделов обязательного ядра, сценарии С1–С8, идеи 5.1–5.18, тестовые аккаунты и большая часть Definition of Done из него сохраняются и реализуются на стеке, описанном ниже. **Осознанные отклонения от 01 — ровно три, все объявлены здесь:**
1. **Бэкенд.** Приложение A продуктового решения рекомендовало Node + Fastify + React — заменено решением команды «бэкенд строго на C++» (ради скорости и производительности на масштабе).
2. **Фронтенд.** Вместо Vite + React + TypeScript + Tailwind — SSR на CSP-шаблонах Drogon + htmx + Alpine.js. Прямое следствие п. 1 (SSR на сервере, без SPA и без npm-сборки); все требования 01 к мобильному-first от 360 px, состояниям экранов и PWA сохраняются.
3. **PWA + push (идея 5.5, P0) — двухфазный план.** Фаза 1 (гарантия демо): WebSocket + Notification API — уведомления доезжают при активной PWA; фаза 2 (усиление, если останется время до 24.11): фоновый web-push по RFC 8291/8292 (2.4). Это ослабляет формулировку DoD №4 из 01 («push виден в обеих учётках»): на демо показываем push в активной PWA; полный фоновый push — цель, но не гарантия, и в описании процесса это фиксируется честно.
Всё остальное продуктовое решение (включая DoD №2 с 403 на чужой id) остаётся источником истины по фичам и приёмке.

**Проверка фактов.** Даты релизов, лицензии и статусы библиотек проверены двумя сессиями: (а) сессия исследования 04.11.2026 — через GitHub API и raw-файлы LICENSE (зафиксировано в материалах исследования команды); (б) эта сессия 04.11.2026 — веб-поиском по ключевым утверждениям (TechEmpower R23, закрытие TechEmpower, Drogon v1.9.14, лицензии sqlite_orm/Wt/oatpp, Docker-образ Drogon, argon2/jwt-cpp, htmx/Alpine.js, libharu). ## 1. Почему C++ — честное обоснование

Требование команды зафиксировано: бэкенд строго на C++. Это требование мы не пересматриваем — но фиксируем честный баланс, чтобы работа над прототипом не провалилась на исполнении.

### 1.1. Что C++ даёт по производительности и масштабированию

1. **Скорость на уровне лучших результатов индустрии.** В TechEmpower Framework Benchmarks Drogon — многолетний лидер среди C++-фреймворков: **1-е место composite-рейтинга в Round 19** (май 2020), а в последнем раунде R23 — **2-е место composite (`drogon-core` ≈1,04 млн баллов, ≈78,5% от лидера — Rust-микрофреймворка may-minihttp) и высший результат среди всех C++-фреймворков раунда** — проверено веб-поиском в этой сессии по [официальной странице](https://www.techempower.com/benchmarks) (Round 23, composite score) и [Wikipedia](https://en.wikipedia.org/wiki/Drogon_(software)). Для «описания работы» это наш главный количественный аргумент выбора C++ (контекст по бенчмаркам — в 2.1).
2. **Память.** Весь прототип — один нативный процесс без рантайма-посредника: RSS ~25–60 МБ (оценка, см. раздел 7) против сотен МБ у типичного JVM-стека. На минимальном российском VPS 1 vCPU / 2 ГБ за ~490 ₽/мес сервер уходит в простой задолго до исчерпания ресурсов — «масштабирование под различное количество пользователей» (задание, строка 42) для прототипа закрыто с запасом в сотни раз.
3. **Модель ввода-вывода.** Drogon построен на неблокирующем event loop (собственная сетевая библиотека Trantor) с асинхронным `DbClient` и пулом соединений: один процесс держит тысячи одновременных соединений без потока на соединение. Это та же архитектурная идея, что у Node/Go, но без GIL и с предсказуемыми паузами (нет сборщика мусора — нет stop-the-world).
4. **Предсказуемость хвостовых задержек.** Генерация HTML (SSR-шаблон компилируется в нативный код), сериализация JSON и генерация PDF — всё нативное; p95 на кэшированном расписании — единицы миллисекунд (оценка). Для жюри это конвертируется в «интерфейс быстрый и доступный» — прямой критерий «Качества».

### 1.2. Чем платим — без прикрас

1. **Скорость разработки.** C++ многословен; полный билд Drogon-проекта — 30–60 с (оценка по опыту сборок Drogon); ассистенты в вайбкодинге чаще ошибаются в сигнатурах C++-API, чем в Python/TS. Это **главный риск проекта** — работа с ним вынесена в 1.3 и в раздел рисков (11).
2. **Экосистема беднее.** Нет django-уровня «админки из коробки», зрелых инструментов миграций, огромного маркетплейса пакетов. Каждую инфраструктурную мелочь (миграции, лимитер попыток входа, генерация PDF) подбираем как маленькую проверенную библиотеку или пишем сами в 50–100 строк.
3. **Стоимость ошибки выше.** Use-after-free или переполнение буфера в Python-прототипе невозможны по построению, в C++ — возможны. В приложении, которое откроет жюри и где по заданию «каждый студент видит только свои данные», это недопустимо — поэтому стиль и сборка зафиксированы жёстко (RAII, умные указатели, sanitizers, параметризованные запросы — раздел 6).
4. **Найм/заменяемость.** Если член команды выпадает, заменить C++-разработчика сложнее, чем Python-разработчика. Для хакатона с ИИ-ассистентами это смягчается тем, что 80% кода — однотипные контроллеры по одному образцу.

### 1.3. Почему для хакатона это допустимо

- **Объём уникальной логики мал.** Прототип — CRUD + SSR + конечный автомат заявки + рассылка уведомлений. Ни одной задачи, где C++ сложнее, чем где-либо ещё: никаких алгоритмов планирования, никакого сырого парсинга бинарных форматов.
- **Критерии жюри** («Проработанность идеи», «Масштаб использования нейротехнологий», «Имплементация», «Качество» — задание, строки 80–84) не содержат ни одного пункта «RPS». C++-выбор нужен не для очков по бенчмаркам, а как честный ответ на требование «стек… гибкий с точки зрения масштабирования» (строка 42) — и как аргумент в описании работы.
- **Всё обязательное ядро закрывается фреймворком, а не ручным кодом.** Это ключевое условие допустимости: с Drogon мы не пишем HTTP-парсер, менеджер сессий, ORM, шаблонизатор или WebSocket-сервер — всё готовое (раздел 2).

### 1.4. Как снимаем главный риск — скорость разработки

| Мера | Конкретно |
|---|---|
| Стартуем не с пустого проекта | Генератор `drogon_ctl create project / create controller / create view` — встроенный scaffolding: каркас CMake + контроллер + CSP-шаблон создаётся командой, а не промптом |
| Фиксируем версии в промптах | В каждом промпте ассистенту: «Drogon v1.9.14, C++20, Boost.Asio off, контроллеры HttpController». Версия Drogon закреплена subproject-ом/тегом, чтобы ассистент не «выдумывал» API другой версии |
| Даём ассистентам реальные сигнатуры | В контекст — заголовки `HttpAppFramework.h`, `HttpController.h`, доки Drogon (wiki ENG-*) и 1–2 готовых контроллера из нашего же репозитория как образец стиля |
| Компиляция | `ccache` + Ninja + инкрементальные сборки; «тонкие» контроллеры (10–30 строк) + SQL через ORM — не ручная работа с памятью; изменения затрагивают 1–2 единицы трансляции |
| Минимум ручного парсинга | JSON — встроенный `Json::Value` Drogon; HTML — CSP-шаблоны, компилируемые в C++-классы; формы — штатный `HttpRequest::getParameters()`; из «парсинга» в проекте остаётся только генерация ICS (обратная задача — конкатенация строк) |
| Ранний чек сборки | Целевая ОС (Ubuntu 24.04, Docker) собирается в первый же вечер хакатона, а не за день до дедлайна 28.11 |

## 2. Стек

### 2.1. Фреймворк: **Drogon v1.9.14** (рекомендация зафиксирована)

**Что проверено.** Сессия исследования (GitHub API/raw-файлы, 04.11.2026): релиз v1.9.14 от 12.10.2026, последний push 04.11.2026, лицензия MIT, официальный Docker-образ `drogonframework/drogon` на Docker Hub обновлён 12.10.2026. Эта сессия веб-поиском подтвердила: v1.9.14 — текущий последний релиз ([GitHub Releases](https://github.com/drogonframework/drogon/releases)), официальный образ Ubuntu-based с предустановленными зависимостями и `drogon_ctl` существует ([Docker Hub](https://hub.docker.com/r/drogonframework/drogon), [wiki: Installation](https://github.com/drogonframework/drogon/wiki/ENG-02-Installation)).

**Пять причин выбора — все проверены:**

1. **Единственный из рассмотренных C++-фреймворков, где для прототипа «личного кабинета» из коробки есть всё обязательное ядро:**
   - **сессии** — `app().enableSession(timeout)` в `HttpAppFramework.h:874` (проверено в сессии исследования) и через `config.json` (`"session": {"cookie_key": "...", "timeout": ...}`) — подтверждено [wiki ENG-07: Session](https://github.com/drogonframework/drogon/wiki/ENG-07-Session);
   - **ORM с PostgreSQL и SQLite3** (README:33–37, подтверждено поиском: «Drogon supports PostgreSQL, MySQL/MariaDB, SQLite3») — `drogon_ctl create model` генерирует слой доступа по схеме БД;
   - **SSR-шаблоны** — CSP (C++ Server Pages): HTML с вставками C++ компилируется в нативные классы представлений, создаются командой `drogon_ctl create view`;
   - **JSON** — встроенный `Json::Value`/`HttpResponse::setJsonObject` без второй зависимости;
   - **статические файлы** — `app().setDocumentRoot()` + отдача Nginx-ом в проде;
   - **WebSocket** — встроенные `WebSocketController` для канала уведомлений.
   У Crow/Pistache/cpprest всё это пришлось бы собирать из 4–6 сторонних библиотек — на хакатоне это дни риска.
2. **Живость и деплой.** Коммиты в день проверки (04.11.2026), релиз v1.9.14 неделей раньше, официальный Docker-образ — деплой собирается за час, а не за вечер.
3. **Лицензия MIT** — ноль юридических вопросов при публикации исходников жюри (требование задания, строка 47).
4. **Производительность** — см. 1.1: TFB R19 (1-е место composite, май 2020) и R23 (2-е место composite, высший результат среди C++-фреймворков раунда).
5. **Узнаваемость для ИИ-ассистентов.** Из C++-фреймворков у Drogon максимальное покрытие в обучающих данных: туториалов, примеров кода и ответов на Stack Overflow (тег `drogon-framework`) больше всего — при вайбкодинге это прямо влияет на критерий «Масштаб использования нейротехнологий»: ассистент реже выдумывает несуществующий API.

**Честная оговорка по бенчмаркам (обязательно для описания работы).** Последний опубликованный раунд — **Round 23** (прогон 24.02.2025, публикация марта 2025). **24.03.2026 (issue TechEmpower/FrameworkBenchmarks#10932, опубликован 23.03.2026 — дата проверена веб-поиском в этой сессии) TechEmpower официально объявил о закрытии проекта** («Sunsetting the TechEmpower Framework Benchmarks»); репозиторий заархивирован. Свежих бенчмарков не будет. В описании работы ссылаемся на R23/R19 именно с этим контекстом: «последний из когда-либо опубликованных раундов» — это корректно и защищает от вопроса «почему цифры старые».

**Запасной вариант — Crow** (header-only, BSD-3-Clause): проще старт, но ORM, шаблоны и WebSocket пришлось бы добирать сторонними библиотеками (ludjs ORM? нет — например, sqlite_orm [запрещён, см. ниже], inja для шаблонов) — на хакатоне это плюс-два интеграционных риска. Crow берём, только если Drogon не соберётся на целевой ОС в первый вечер.

**Что не берём и почему (все лицензии проверены):**

| Библиотека | Причина отказа |
|---|---|
| oatpp (Oat++) | Apache-2.0, но разработка затухла: последний релиз 1.3.1 (2022); в июне 2025 раскрыта уязвимость CVE-2025-6566 (stack-based buffer overflow), патченного релиза нет — проверено поиском в этой сессии; PostgreSQL-адаптер в alpha |
| sqlite_orm | С релиза v1.9.1 (03.02.2025) лицензия **AGPL-3.0 + платный MIT** — release notes: «license changed from BSD3 to GNU AGPL + paid MIT» (проверено поиском; сама идея dual-licensing обсуждалась в issue #3 ещё с 2017 г.): AGPL неприемлем в репозитории для публикации, а платная лицензия — не наш путь |
| Wt (Webtoolkit) | GPL-2.0 (+коммерческая), проверено поиском; плюс виджетная модель «веб без HTML» не для мобильного-first кабинета с кастомным дизайном |

| Pistache, cinatra, libhttpserver | HTTP-роутинг без сессий/ORM/шаблонов — пришлось бы добирать всё из 1-го пункта |

### 2.3. Фронтенд: почему SSR + htmx + Alpine достаточно для mobile-first 360 px

- **SSR как основа.** Страницы рендерит сервер (CSP-шаблоны): первый рендер быстрый даже на слабом телефоне, работает без JS — «нужное находится за пару касаний» не требует SPA.
- **htmx** закрывает 90% интерактивности: формы заявки и смены статусов, фильтры очереди сотрудника, «пометить прочитанным», лента уведомлений — частичные обновления фрагментов HTML без перезагрузки. Это буквально «React без React»: нет сборки, нет npm, нет состояния-рассинхрона. Один нюанс учтён: в htmx 2.0 атрибуты `hx-ws`/`hx-sse` вынесены из ядра в расширения (подтверждено поиском), поэтому WebSocket-логика пишется на ~50 строк своего JS (см. 2.4).
- **Alpine.js** — локальная интерактивность: раскрытие/сворачивание списков, табы «Сегодня/Неделя», показ/скрытие пароля, клиентская валидация формы до отправки, тёмная тема. Всё это — атрибуты в разметке, без сборочного шага.
- **Оба файла ~10–15 КБ gzip**, вендорятся в `/static/vendor/` рядом с бинарником. **Никаких Google Fonts/jsdelivr/unpkg**: жюри открывает из России — CDN под нагрузкой могут тормозить или быть недоступны; шрифт — один самохостящийся (лицензия проверяется при вендоринге).
- **PWA**: `manifest.json` + service worker (кэш последнего расписания и ленты, офлайн-пометка «данные на момент 12:40» — состояние из 4.2 продуктового решения). Инсталляция на рабочий стол нужна и для push на iOS (iOS Web Push работает только для PWA на главном экране, iOS/iPadOS 16.4+ — факт из продуктового решения 5.5 со ссылками на WebKit/Apple).

### 2.4. Канал push-уведомлений на C++ — честный план

Готовой C++-библиотеки web-push в проверенном списке нет, поэтому фиксируем двухступенчатый план:

1. **Базовый канал (демо-гарантия): WebSocket + service worker.** Drogon отдаёт `/ws` (WebSocketController); после входа страница и service worker держат соединение; уведомление приходит JSON-событием `{type, title, body, deep_link}` и показывается через `Notification API`, когда PWA активно. Это покрывает DoD №4 продуктового решения: перенос пары и смена статуса заявки видны в обеих учётках пары anya.demo/oleg.demo.
2. **Фоновый web-push (усиление, если останется время):** реализация RFC 8291 (шифрование payload aes128gcm) и RFC 8292 (VAPID: JWT ES256 на P-256) поверх OpenSSL — связка из примитивов, которые OpenSSL даёт нативно; объём ~300–400 строк + подписки в таблице `push_subscriptions`. VAPID-ключи — только в `EnvironmentFile` на сервере (требование задания, строка 51). Если к 24.11 не готово — демо честно опирается на канал 1, ленту и бейдж непрочитанных; в описании работы это фиксируется как осознанное ограничение, а не скрытая дыра.

### 3.2. Потоки данных

**Поток 1 — SSR-страница («Расписание → Неделя»).**
`GET /schedule` → Nginx → роутер Drogon → `LoginFilter` (нет сессии → 303 `/login`) → `ScheduleCtrl::week()` → `ScheduleCache`: если расписание группы (из профиля по `user_id` сессии) в `CacheMap` — берётся из памяти; иначе один параметризованный запрос `WHERE group_id = :gid AND starts_at BETWEEN :from AND :to` → данные кладутся в модель представления → CSP-шаблон `week.csp` рендерит HTML (пользовательские строки экранируются ДО вставки в view-данные — автоэкранирования в csp v1.9.14 нет, Р-16) → 200 `text/html`. Ветка изменений недели — второй параметризованный запрос по `status != 'normal'`.

**Поток 2 — форма через htmx («сотрудник меняет статус заявки»).**
`POST /v1/applications/{id}/status` с заголовком `HX-Request` → `LoginFilter` + `StaffFilter` (не staff → 403) + CSRF-проверка → `StaffCtrl::changeStatus()` → валидация перехода по автомату (`ready → issued` да; `issued → in_progress` нет → 409) → транзакция: `UPDATE applications ...`, вставка в `application_events` (таймлайн), вставка в `notifications` автору заявки → `NotifyDispatcher`: тихие часы? тип заявки разрешён тумблером? → WebSocket-событие + (фаза 2) web-push → ответ: htmx-фрагмент HTML карточки заявки в новом статусе (200) — очередь сотрудника перерисовывается без перезагрузки.

**Поток 3 — WebSocket-уведомления.**
Страница после входа открывает `wss://…/ws`; `WsCtrl` проверяет сессию, регистрирует соединение в реестре `user_id → connection`. `NotifyDispatcher` пишет уведомление в БД (источник истины) и пушит живым соединениям. Переподключение — свой мини-JS с экспоненциальной задержкой (htmx 2.0 не делает WS в ядре — учтено в 2.3).

**Поток 4 — фоновые напоминания.**
Таймер event loop (trantor `runEvery`, раз в минуту) работает по двум источникам. (а) Базовое напоминание «за 1 день»: выбирает дедлайны с `due_at` в окне и `reminded = 0` → одним батчем создаёт `notifications` (тип `deadline`) всем участникам группы (или владельцу персонального) → ставит `reminded = 1` (флаг означает «базовая рассылка по дедлайну сделана»). (б) Персональные «Напомнить за день» (кнопка дедлайн-радара, 5.2): таймер выбирает строки `deadline_reminders` с `remind_at` в окне и `sent_at IS NULL`, создаёт уведомление владельцу, ставит `sent_at`. В обоих случаях применяются тихие часы — ночью копится в утренний дайджест, кроме срочных (перенос ближайшей пары — правило из 5.6 продуктового решения).

**Поток 5 — PDF-справка (идея 5.3).**
`GET /v1/applications/{id}/pdf` → владение проверено (`OwnershipGuard`) + статус `ready|issued` → `PdfBuilder` (libharu): данные профиля из БД, диагональный штамп «ДЕМО · вымышленные данные», встроенный TTF-шрифт для кириллицы → `HPDF_SaveToStream` → 200 `application/pdf`.

## 4. Модель данных

Отличие от эскиза в Приложении A продуктового решения одно, и оно осознанное: `group_name`-строки нормализованы в таблицу `groups(id, name)` — иначе нельзя индексно выбирать расписание группы, строить рассылку переносов и гарантировать целостность. Семантика всех остальных сущностей сохранена.

Диалект — SQLite (основа). Для PostgreSQL-опции: `TEXT`-времена заменяются на `timestamptz`, `INTEGER`-флаги на `boolean`, остальное идентично. Все времена — ISO 8601 UTC в формате `YYYY-MM-DDTHH:MM:SSZ`.

## 5. API

### 5.1. Принципы

- **Две плоскости.** SSR-страницы (`/`, `/login`, `/schedule`, `/grades`, `/applications`, `/notifications`, `/profile`) отдают HTML и не версионируются. Данные и htmx-фрагменты — под префиксом **`/v1/`**: версия в пути, обратной совместимости внутри хакатонного прототипа не обещаем, но префикс фиксирует контракт для жюри и для фоновых скриптов.
- **Владение — в SQL, а не в коде после выборки.** Каждый запрос к персональному объекту содержит `WHERE user_id = :session_user_id` (или проверку `OwnershipGuard` перед отдачей). Чужой существующий объект → **403** (фиксация по DoD продуктового решения); несуществующий → 404.
- **Единый формат ошибки** (JSON): `{"error": {"code": "forbidden", "message": "Доступ только к своим данным"}}`. Для htmx-запросов ошибка валидации/бизнес-правила отдаётся HTML-фрагментом с сообщением + `HX-Retarget` при необходимости; коды HTTP при этом те же.
- **Коды:** 200/201/204 — успех; 303 — редирект неавторизованного на `/login` (браузерный сценарий); 400 — валидация; 401 — сессия истекла (для API-клиентов); 403 — чужой объект / нет роли; 404 — нет объекта; 409 — недопустимый переход статуса заявки; 429 — лимит попыток входа; 500 — неожиданное (без стека наружу, детали в серверном логе).
- **Content negotiation по `HX-Request`:** контроллер возвращает JSON для API-клиентов и HTML-фрагмент для htmx — один обработчик, два представления.
- State-changing — только POST/PUT/DELETE; GET — только чтение (безопасность при предзагрузке ссылок).

## 6. Безопасность

Требования задания (строки 48–51): «каждый студент видит только свои данные — чужой профиль или чужую заявку не открыть, даже подставив другой адрес»; «пароли не хранятся в открытом виде»; «ключи и пароли от сервисов… не лежат в коде и в браузере пользователя».

### 6.1. Аутентификация и сессии

- **Сессии, не JWT.** Для классического кабинета с cookie-доменом и SSR сессии+cookie проще и безопаснее, чем JWT (нет места хранения refresh-токена в браузере, нет проблемы отзыва). Встроенная сессия Drogon (`enableSession`, cookie-ключ настраивается, таймаут в `config.json` — wiki ENG-07) или собственный фильтр поверх таблицы `sessions`. **Фиксируем собственный вариант:** cookie с случайным 128-бит токеном → таблица `sessions` (риск 6: перезапуск бинаря не убивает сессии жюри), флаги cookie `HttpOnly; Secure; SameSite=Lax` выставляет единый хелпер выдачи cookie; выход — `DELETE FROM sessions` (инвалидация на сервере).
- Таймаут сессии — достаточный на весь период оценивания (до 28.11 включительно), продление при активности.
- **JWT** (jwt-cpp, MIT — проверено) остаётся запасом только для межсервисного сценария, которого в прототипе нет.

### 6.2. Хеширование паролей

- **Argon2id** через phc-winner-argon2 (CC0/Apache-2.0): `argon2id_hash_encoded(t=2, m=19456 КБ, p=1, …)` — параметры по рекомендации OWASP Password Storage Cheat Sheet; проверка — `argon2id_verify()` (constant-time сравнение внутри библиотеки). Salt генерирует библиотека, в БД — только encoded-строка.
- **MD5/SHA256 из Drogon `Utilities.h` для паролей запрещены** код-ревью правилом (они есть в API и предназначены для других задач) — библиотека argon2 подключается явно, это прямой ответ на требование строки 50.
- Демо-пароль жюри фиксированный и публикуется только в комментарии к работе; в БД и логах — только хэши (продуктовое решение, Приложение A).

### 6.3. Изоляция данных студента — «подставить адрес не выйдет»

Трёхуровневая схема, одинаковая на каждом эндпоинте:

1. **`LoginFilter`** на всех приватных роутах: нет сессии → 303 `/login` (SSR) / 401 (API).
2. **Скоуп в самом запросе:** `SELECT … FROM applications WHERE id = :id AND user_id = :session_user` — чужой id просто не совпадёт со строкой; списки всегда `WHERE user_id = :session_user`.
3. **`OwnershipGuard`** для объектов, где id приходит в пути (`applications/{id}`, `grades/{id}`, `notifications/{id}`): одна функция, проверяющая владение до любой отдачи данных; исключить её использование невозможно код-ревью правилом «контроллер с path-id обязан вызвать guard».

Результат: чужая заявка/профиль/оценка **не отдаются никогда** — подстановка адреса даёт 403 (существующий чужой объект) или 404 (несуществующий). Это свойство сервера, а не скрытие ссылок на клиенте (продуктовое решение, строка 11). Автотест — раздел 9.3.

- **RBAC:** `StaffFilter` на `/v1/staff/*`; студент, вызвавший staff-эндпоинт, получает 403. Две роли (`student`, `staff`) — по границе из 7.8 продуктового решения.
- **Расписание:** фильтр по своей группе строится на сервере из профиля, параметр группы от клиента не принимается (4.2 продуктового решения).

### 6.4. CSRF, XSS, SQL-инъекции

- **CSRF:** `SameSite=Lax` отсекает кросс-сайтовые POST-ы браузера; поверх — токен double-submit (cookie `csrf` + скрытое поле/заголовок, проверка в `CsrfCheck`) и требование заголовка `HX-Request` для htmx-эндпоинтов; state-changing только POST/PUT/DELETE.
- **XSS:** автоэкранирования в CSP-шаблонах Drogon v1.9.14 **нет** — синтаксиса `{{}}` в этой версии не существует, вывод переменных `[[ имя ]]` / `<%c++ $$ … %>` сырой (проверено по парсеру drogon_ctl/create_view.cc v1.9.14 при каркасе Э7, Р-16). Правило проекта: пользовательские данные попадают в шаблон только уже экранированными — `HttpViewData::htmlTranslate` в рендер-вызове или экранирование в сервисе; сырой вывод — только для серверных констант, ревью-правило (образец — `views/partials/head.csp`: title через htmlTranslate). Переведённые UI-строки (5.18) — те же серверные константы: словарь `t(key, lang)` подставляется в view-данные ДО рендера и проходит по этому правилу целиком; `lang`-атрибут `<html>` в head.csp ставится динамически по языку запроса (cookie `para_lang` → `Accept-Language` → ru; выбор хранится в `settings.lang`). Заголовки ответа: `Content-Security-Policy: default-src 'self'` (никаких внешних CDN — и безопасность, и доступность из РФ совпадают), `X-Content-Type-Options: nosniff`, `frame-ancestors 'none'`.
- **SQL-инъекции:** **все** запросы — параметризованные (`DbClient` binding / сгенерированный ORM); конкатенация строк в SQL запрещена правилом проекта и является главным вектором, который мы исключаем архитектурно: контроллеры SQL-строк не формируют вообще.
- **Лимит попыток входа:** счётчик `failed_attempts` + `locked_until` в `users` (нарастающая задержка — состояние из 4.1 продуктового решения), ответ 429.

### 6.5. Секреты, TLS, эксплуатация

- **Секреты только вне кода и вне браузера:** `EnvironmentFile=/etc/app/env` (секрет БД, ключ сессий, VAPID-ключи фазы 2), `.env`-файлы в `.gitignore`, в репозитории — только `env.example` без значений. В клиентский код не выносится ничего, кроме данных сессии; QR и PDF строятся из данных профиля сервером/по сессии.
- **TLS:** Let's Encrypt на Nginx, HSTS; HTTP → HTTPS redirect; cookie с флагом `Secure` не уйдёт по HTTP.
- **Логи** не содержат паролей, токенов сессий и `push_subscriptions.keys` — фильтрация на уровне логгера.
- **Память/UB:** RAII, умные указатели, `std::string`, никаких `new/delete` вручную; тестовые сборки с `-fsanitize=address,undefined`.
- **Изоляция процесса:** запуск под непривилегированным пользователем, systemd-харднинг (`NoNewPrivileges`, `ProtectSystem=strict`, `PrivateTmp` — unit в 8.2).

## 7. Производительность

### 7.1. Индексы и кэш

- **Индексы** — 4.2: каждый пользовательский сценарий ведёт по составному индексу, full scan по пользователям/оценкам/уведомлениям недостижим по построению.
- **Кэш расписания:** `drogon::CacheMap<group_id, WeekModel>` с TTL 60 с + мгновенная инвалидация при сохранении переноса сотрудником (`ScheduleCache::invalidate(group_id)` из той же транзакции). Один запрос к SQLite обслуживает всю группу — самый частый экран «Сегодня» не трогает БД вовсе.
- **Кэш дашборда:** агрегат «Сейчас важно» — 30 с на пользователя; бейдж непрочитанных — инкрементально.
- **Статика:** Nginx отдаёт `/static/*` с `Cache-Control: max-age=31536000, immutable` (хэш в имени файла), сжатие gzip/brotli на edge; процесс Drogon статику в проде не отдаёт.
- **SQLite:** WAL-режим (чтение не блокирует запись), `synchronous=NORMAL`, `cache_size` в пределах 32 МБ; пул соединений Drogon — 4–8.
- **Фоновая рассылка переносов** — батчем одним `INSERT … SELECT` по составному индексу группы, не построчно.

### 7.2. Почему C++ даёт запас по числу пользователей

- Один из лучших composite-результатов в последнем раунде TFB (R23: **2-е место**, ≈1,04 млн, ≈78,5% от лидера may-minihttp; **высший среди C++-фреймворков раунда**; №1 composite — R19, май 2020 — см. 1.1): рамка производительности подтверждена внешним замером, а не нашим обещанием.
- Один процесс, event loop, нулевая работа GC: память не растёт с числом соединений, пауз нет; CRUD-нагрузка упирается в SQLite/диск задолго до CPU.
- Генерация SSR-HTML — компилированный шаблон, PDF — нативная libharu: даже «тяжёлые» операции прототипа дешевле, чем интерпретируемые аналоги.

## 8. Деплой

### 8.1. Docker (основной путь)

Multi-stage, зависимости — системными apt-пакетами (риск 3):

```dockerfile
# ---- сборка ----
FROM drogonframework/drogon:1.9.14 AS build   # официальный образ, все зависимости Drogon внутри
WORKDIR /src
COPY . .
RUN apt-get update \
 && apt-get install -y --no-install-recommends ninja-build ccache \
 && cmake -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
 && cmake --build build -j"$(nproc)"   # + libharu из исходников (v2.4.6) на этом слое

# ---- рантайм ----
FROM ubuntu:24.04
RUN apt-get update \
 && apt-get install -y --no-install-recommends \
      libsqlite3-0 libssl3t64 libargon2-1 ca-certificates sqlite3 tzdata \
 && rm -rf /var/lib/apt/lists/*
COPY --from=build /src/build/para      /opt/para/para
COPY --from=build /src/views           /opt/para/views
COPY --from=build /src/static          /opt/para/static
COPY --from=build /src/sql             /opt/para/sql
RUN mkdir -p /opt/para/data && chown -R 10001:10001 /opt/para/data
WORKDIR /opt/para
USER 10001
EXPOSE 8080
ENTRYPOINT ["/opt/para/para", "--config", "/etc/app/config.json"]
```

Рантайм-слой — без компилятора: итоговый образ ~200 МБ. База данных — именованный том `para-data:/opt/para/data`: при первом монтировании пустого тома Docker переносит на него права каталога из образа (владелец 10001) и `USER 10001` может писать; если том создаётся вручную или переиспользуется на другом хосте — разовый `chown 10001:10001` внутри одноразового контейнера с этим томом. Сборка воспроизводится одной командой `docker compose up --build`; имена runtime-пакетов фиксируем при первом прогоне на Ubuntu 24.04 (early check — 1.4).

## 9. Тестирование

### 9.1. Unit-тесты (doctest, MIT)

Покрытие — логика, где цена ошибки максимальна:
- **Конечный автомат заявки:** все допустимые/недопустимые переходы (`ready → issued` ок; `issued → in_progress` → ошибка 409); генерация событий таймлайна.
- **OwnershipGuard:** владение/чужое/несуществующее.
- **NotifyDispatcher:** тумблеры, тихие часы (ночное — в дайджест; срочный перенос ближайшей пары — сразу), deep link.
- **IcsBuilder:** корректность VCALENDAR/VEVENT, UID, UTC-времена, отзыв токена.
- **PasswordHasher:** round-trip argon2id, отказ от коротких хэшей.
- **Limiter входа:** нарастающая задержка и сброс после успеха.

### 9.2. Интеграционные тесты

Тестовый бинарь поднимает приложение на временной SQLite с фикстурами (`fixtures.sql`), стучится собственным `HttpClient` Drogon на loopback-порт:
- вход/выход, cookie-флаги, повторный вход;
- сценарии С1–С8 как HTTP-последовательности (по одному тесту на шаг сценария из раздела 3 продуктового решения);
- ICS-эндпоинт: подписка реально читается (парсим результат тестовым клиентом);
- PDF: заголовок `%PDF-`, наличие штампа «ДЕМО» (текстовый поиск в потоке).
- бронь аудитории (5.10): бронь свободного слота → повторная бронь того же слота другим клиентом → 400; `DELETE` чужой брони → 403.

Сборки с `-fsanitize=address,undefined` — тесты обязаны проходить под санитайзерами (риск 2: память). Запуск: `cmake --build build-tests && ctest --output-on-failure`.

### 9.3. Автотест безопасности — прямая проверка критерия жюри

Два клиента с разными сессиями (anya.demo и oleg.demo — у них одна группа 1-ФМО, поэтому различие проверяем именно на личных объектах):

## 11. Риски и меры (сводно)

№ | Риск | Мера
---|---|---
1 | **Скорость разработки**: многословность C++, билд 30–60 с, ассистенты чаще ошибаются в сигнатурах | `drogon_ctl`-scaffolding; фиксация «Drogon v1.9.14, C++20» в каждом промпте; реальные сигнатуры из заголовков в контексте ассистента; ccache + инкрементальные сборки; тонкие контроллеры + ORM вместо ручной работы с памятью (1.4)
2 | **Безопасность памяти (UB)** в приложении, которое откроет жюри | RAII/умные указатели/`std::string`, никаких `new/delete`; `-fsanitize=address,undefined` в тестах; SQL только параметризацией; пароли — только libargon2; авторизация в едином фильтре, не в каждом хендлере; systemd-изоляция и непривилегированный запуск
3 | **Хрупкая сборка** (CMake + sqlite + OpenSSL + argon2 на разных машинах) | Docker multi-stage с первого дня, зависимости — apt-пакетами; early check сборки на целевой ОС в первый вечер, не перед дедлайном
4 | **«Производительность» не окупается в критериях жюри** (они про UX, сценарии и ИИ-процесс) | C++-выбор обосновываем в описании работы цифрами TFB R23/R19 (с контекстом закрытия TechEmpower 23–24.03.2026) и памятью одного процесса; трудимся в первую очередь над мобильным UX 360 px, пустыми состояниями и заявкой за три касания; сервер на минимальном VPS показывает десятки тысяч RPS и без оптимизаций
5 | **Нет зрелой экосистемы миграций/админки** как в Django-мире | Схема — 4 читаемых SQL-миграции + `schema_migrations`; фикстуры с вымышленными данными; демо-аккаунты; README с командой запуска; все лицензии пермиссивные (MIT/BSD/Apache/ISC/CC0) — публикация исходников жюри без юридических вопросов
6 | **Сессии в памяти теряются при перезапуске** (сессии жюри!) | Сессии в таблице `sessions` (SQLite/PostgreSQL), cookie — только случайный токен; серверная проверка владения по `user_id` из сессии на каждый запрос — подстановка URL не открывает чужое даже после рестарта

## Приложение А. Порядок первого вечера (снятие риска сборки)

1. `docker pull drogonframework/drogon:1.9.14` → `drogon_ctl create project para` → сборка и запуск пустого каркаса (точка отсчёта).
2. Подключить libargon2, собрать «hello + Argon2id round-trip».
3. Поднять SQLite-файл, прогнать миграции 0001–0008, создать демо-пользователей фикстурами.
4. Собрать `LoginFilter` + один защищённый эндпоинт + один CSP-шаблон — сквозной вертикальный срез «вход → страница».
5. Прогнать автотест 9.3 на каркасе (красный) — дальше фичи реализуются так, чтобы он стал зелёным.
6. Задеплоить каркас на VPS и открыть с телефона — ссылка для жюри живёт с первого дня, дальше только обновляется.

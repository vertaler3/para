**Версия:** 1.0 · **Дата:** 04.11.2026 · **Статус:** утверждено командой; документ — рабочий план для агентов-исполнителей и заготовка раздела «описание процесса» для PDF-отчёта.
**Входные документы:** «Хакатон от мгимо - вайбкодинг.md» (задание), «решения/01-продуктовое-решение.md», «решения/02-техническое-решение.md», «решения/03-дизайн-решение.md». Отдельный справочный обзор зарубежных аналогов (лежит рядом в папке) во входные документы кодирования не входит и при написании кода не используется.

## 1. Что строим

Строим **«Пару»** — работающий прототип личного кабинета студента «деканат в кармане»: главный экран «Сейчас важно» отвечает на вопрос «что мне делать сегодня», расписание показывает переносы как события первого класса («было → стало» + push), заявка на справку — конечный автомат с таймлайном из 5 точек, как трекинг заказа, каждое уведомление ведёт к объекту, а всё ядро (вход и профиль, расписание, успеваемость, заявки, уведомления — задание, строки 29–33) спроектировано mobile-first от 360 px на токенах с двумя палитрами и продуманными состояниями; прототип — монолит C++20 на Drogon v1.9.14 + SQLite с SSR-шаблонами CSP + htmx + Alpine.js (без npm-сборки и внешних CDN), серверной проверкой владения каждым объектом (чужой id → 403), Argon2id-хэшами паролей и деплоем на российский VPS с самохостящимися ассетами. Продукт, персоны, сценарии С1–С8, идеи 5.1–5.10 и Definition of Done зафиксированы в «решения/01-продуктовое-решение.md»; техническая реализация (стек, модель данных, API, безопасность, деплой) — в «решения/02-техническое-решение.md», который объявляет ровно три отклонения от 01: бэкенд C++/Drogon вместо Node+Fastify, SSR вместо Vite+React+Tailwind, двухфазный push (WebSocket — демо-гарантия, фоновый web-push — усиление); дизайн-система, вайрфреймы всех экранов, тексты состояний и айдентика — в «решения/03-дизайн-решение.md». Жёсткие ограничения задания действуют на всём пути: только вымышленные данные, бейдж «концепт для хакатона» на всех экранах, без логотипа вуза, пароли только хэшами, ключи только на сервере, прототип доступен из России без VPN до 28 ноября.

Пояснения по ключевым решениям структуры:

- **`src/controllers` — тонкие, `src/services` — толстые.** Правило 02 §3.1: контроллер 10–30 строк, вся логика в сервисах; владение объектом проверяет один `OwnershipGuard` — код-ревью правило «контроллер с path-id обязан вызвать guard» (02 §6.3). Это же — чек-лист для агентов-ревьюеров (см. §4.4).
- **`views/` компилируются в бинарник** (CSP → C++-классы через `drogon_ctl create view`), поэтому «фронтенд» в репозитории — это шаблоны + чистый CSS на токенах; ни сборочного шага, ни npm, ни внешних CDN — ассеты самохостятся и открываются из РФ без VPN (02 §2.3).
- **`sql/` — документация схемы для жюри:** 4 читаемых миграции + фикстуры с вымышленными данными; миграции применяются при старте приложения, отдельного шага деплоя нет (02 §8.3).
- **`tests/security_tests.cpp` живёт в репозитории постоянно** — это фактическая проверка критерия задания «чужой профиль не открыть, даже подставив адрес» (строка 49), вывод теста прикладываем к PDF-отчёту (02 §9.3).
- **`docs/agents-log/` — часть продукта, а не побочная папка:** по критерию «Масштаб использования нейротехнологий» жюри оценивает фиксацию промптов и работы с ошибками ИИ; журнал пишется по ходу (см. §4.3), не задним числом.

### 2.1. AGENTS.md — живой файл продолжения работы

`AGENTS.md` в корне репозитория — первая точка входа для любого человека или ИИ-агента, продолжающего работу. Прототип файла создан в рабочей области рядом с `решения/` и переносится в репозиторий на Э1 без изменений.

**Обязательные разделы файла:** что это за проект и бейдж-дисклеймер; где лежат решения и в каком порядке читать; стек и фактически работающие команды (сборка, тесты, запуск, миграции — заполняются на Э1 и поддерживаются актуальными); соглашения (вымышленные данные, argon2id, secrets в env, проверка лицензий, тонкие контроллеры, токены 03, сохранение промптов); **текущий статус** (этап, что готово, как проверить); **протокол ведения**; **открытые вопросы**.

**Правила ведения (обязательные, проверяются на чекпоинте каждого этапа):**

1. Этап закрыт = коммит, обновляющий AGENTS.md: раздел «Текущий статус» (этап, артефакты, как проверить) и «Открытые вопросы». Этап без обновления AGENTS.md не считается закрытым.
2. Каждая сессия (человек или агент) начинается с чтения AGENTS.md; каждый промпт агенту начинается с фразы «Прочитай AGENTS.md в корне репозитория» — это правило включено в шаблоны промптов §4.2.
3. Изменили решение — сначала запись в `docs/decisions.md`, затем правка документа в `решения/`, затем AGENTS.md. Так файл всегда описывает актуальное состояние, а не намерения.

### 4.4. Как ловим и чиним ошибки ИИ

Пять гейтов, через которые не проходит ни один результат агента:

1. **Гейт сборки и тестов.** Ничто не считается готовым без зелёных `cmake --build && ctest --output-on-failure` под `-fsanitize=address,undefined`. Интеграционные тесты С1–С8 и security-тест — обязательные части прогона.
2. **Контракт промпта против галлюцинаций.** Версия и сигнатуры зафиксированы в каждом промпте («Drogon v1.9.14, C++20, Boost.Asio off…»), прямое правило «не уверен — скажи, не выдумывай», в контекст даются заголовки Drogon и 1–2 готовых контроллера как образец стиля (мера из 02 §1.4, риск №1).
3. **Красный тест до фичи.** Тест на требование пишется и падает до реализации (security-тест красный с первого вечера — 02, прил. А п. 5): фича считается готовой, только когда тест позеленел, — так агенты не «отчитываются» словами.
4. **Ревьюер-агент + человек.** Промпт 4 на каждый дифф; финально дифф читает человек. Всё, что агент сделал мимо чек-листа, откатывается; ошибка фиксируется в `agents-log/`.
5. **Правило библиотек.** Любая зависимость — только после карточки «лицензия + дата последнего коммита» (урок Fedena и отбракованные sqlite_orm/Wt/oatpp — 02 §2.1); лицензия вендоренного шрифта/QR-библиотеки проверяется при подключении (02, прил. Б).

# 21.11.2026 — дефект «пустые Новости/События» после a121e83 (ветка `final_fixes_v1`)

Заявка: после коммита a121e83 (смешанная лента «Новости», 20.11) сегменты
«Новости»/«События» пустуют у владельца, хотя коммит заявлял рабочее
состояние (скриншоты `docs/screens/2026-11-20-объявления/`, журнал
`2026-11-20-ai-ассистент.md`).

## 1. Воспроизведение (по фактам, без догадок)

**(а) API на живом томе (до пересева):** вход anya.demo →
`GET /v1/news` → `{"news":[],"next_cursor":null}` — ПУСТО;
`GET /v1/announcements` → 1 строка («Деканат ФМО: приём в ноябре»),
`next_cursor:null`. Прямой sqlite: `news=0, announcements=1, users=32`.

**(б) Браузер на том же контуре (до пересева):** вкладка «Новости» —
**работает**: `data-segment=news`, список видим, 1 строка-объявление с
бейджем «Объявление» (текст совпадает с API), error/empty скрыты;
resource-тайминги: `/v1/news` и `/v1/announcements` оба **200**. Вкладка
«События» — корректное пустое состояние «Событий пока нет» (событий в
news=0 нет вовсе). JS-ошибок на экранную логику нет — рендер идёт.

**(в) Статика:** `GET /static/js/app.js` — md5 отданного файла ==
исходнику (`loadMixedNews` и `annCursor` в теле присутствуют, 334191 байт);
заголовки: `last-modified` актуальный, `expires` динамический — кэш
старого app.js исключён.

**Чистый пересев (прецедент Э8: `down -v && up -d --build`):**
`news=9`; `GET /v1/news` → 8 строк (аудитория Ани) + `next_cursor:null`,
`/v1/announcements` → 1. Браузер: «Новости» — **9 строк** (8 новостей с
категориями + 1 объявление, свежие сверху, первая — 学生会「桌游之夜」
12.11), «События» — **7 строк**. Скриншоты до/после —
`docs/screens/2026-11-21-новости-дефект/`.

## 2. Причина

**Сервер/данные, не клиент.** a121e83 (loadMixedNews) исправен: на пустых
данных честно показал 1 объявление, на полных — 9 строк. Живой том
демо-контура засеян **до 12.11** — раньше, чем news-блок (53c7278, фича
5.17) попал в `sql/fixtures.sql`; маркер `fixtures` в schema_migrations
корректно блокирует повторное сидирование (Р-5/Р-8 — by design), и все
ДОБАВЛЕНИЯ в фикстуры после первого сида в старый том не попадают никогда:
`/v1/news` отвечает пустым массивом → «События» пусты (честно), «Новости»
без новостей (только объявление). Таблица `users=32` вводила в заблуждение
— это фикстуры v2 (10–11.11), news добавлены ПОЗЖЕ них (12.11).

Кандидаты-клиенты отпали по фактам (а)–(в): API пуст — значит сервер;
JS-ошибок и кэша статики нет.

## 3. Фикс: детекция устаревшего сида в MigrationRunner

Пересев руками лечит любой том, но дефект молчал — раннер при пропуске
сида не отличал «файл не менялся» от «файл изменился после сида». Фикс
(не авто-перезаливание — в демо-контуре могут быть живые изменения):

- при применении фикстур рядом с маркером `fixtures` записывается строка
  `fixtures-digest-<FNV-1a 64 hex>` (отпечаток файла; `fileDigest`
  публичен для тестов);
- при seed-старте с уже применёнными фикстурами отпечаток сверяется с
  текущим `fixtures.sql`: расхождение ИЛИ отсутствие digest-строки (сид
  старее детекции — ровно случай владельца) → `Result::fixturesStale` +
  **WARN** в лог с обоими отпечатками и инструкцией
  `docker compose down -v && docker compose up -d --build`; итоговая
  строка раннера дополняется «фикстуры уже были, НО УСТАРЕЛИ»;
  совпадение → INFO «фикстуры уже применены и не изменились».

Живой прогон на «старом» томе (том пересеян до фикса, digest-строки нет):
WARN «сид старее детекции изменений фикстур» — причина видна в логах
контейнера сразу. Чистый сид после фикса: «фикстуры применены» +
digest-строка в schema_migrations; повторный рестарт — INFO без WARN.

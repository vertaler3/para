## Шаг 1 — миграция 0007_news (таблица news + индекс)

**Постановка.** Создать `sql/migrations/0007_news.sql`: таблица
`news(id PRIMARY KEY, category TEXT NOT NULL CHECK (category IN
('official','conference','org','event')), title TEXT NOT NULL, body TEXT,
event_at TEXT nullable, location TEXT nullable, audience TEXT NOT NULL DEFAULT
'all' CHECK (audience IN ('all','group','course')), audience_value TEXT,
published_at TEXT NOT NULL)` + индекс `idx_news_published(published_at DESC,
category)`. Поля — дословно из постановки, стиль — как у 0001–0006, даты —
ISO 8601 UTC, идентификаторы — по конвенциям фикстур. Проверить по
MigrationRunner, что файл подхватится автоматически (порядок, user_version → 7);
юнит-тест раннера — обновить, если ассертит количество/версию. FK-политика Р-24
(Э8): таблица без внешних ключей, но удостовериться, что гейт
foreign_key_check проходит. Проверка шага — контейнерная сборка + ctest.

**Что сделал.**
- Прочитал перед написанием: все миграции 0001–0006 (стиль шапок/DDL/индексов),
  `src/services/MigrationRunner.{h,cpp}`, `tests/unit/migration_runner_test.cpp`,
  `tests/security_tests.cpp:716–758` (предусловие миграций), `sql/fixtures.sql`
  (шапка-конвенции), журнал Э6а шаг 1 (прецедент миграционного шага).
- Написал `sql/migrations/0007_news.sql`: таблица `news` (9 колонок дословно из
  постановки; `id INTEGER PRIMARY KEY AUTOINCREMENT` — форма «id PRIMARY KEY»
  проекта) и `idx_news_published ON news(published_at DESC, category)`. Без
  BEGIN/COMMIT — границы ставит раннер (Р-5). Фикстуры/сервис/контроллеры —
  следующие шаги.
- Быстрая SQL-проверка на хосте (sqlite 3.51.0): свежая БД + файл 0007 →
  таблица и индекс созданы; вставка с audience DEFAULT 'all' (audience_value
  NULL) и с audience='group'/'1' + event_at + location — обе проходят;
  `INSERT ... category='bad'` отклонён CHECK-ом; `PRAGMA foreign_key_check` —
  пусто. Попутно поймана моя же ошибка в тест-вставке (см. «Ошибки»).
- Проверка «применяется при старте» по коду раннера (см. «Решения», п. 1):
  0007 подхватится автоматически, user_version станет 7; юнит-тест раннера и
  security_tests количество миграций не ассертят — правок тестов не требуется.
- Контейнерная проверка шага: сборка + ctest (команда и числа — ниже, в
  «Финальный прогон»).

**Решения.**
1. **Автоподхват 0007 раннером — по коду, без правок раннера:**
   `MigrationRunner::collectMigrations` (MigrationRunner.cpp:217–250) берёт из
   каталога все `.sql` с числовым префиксом NNNN и сортирует по возрастанию
   (лексикографика == числовая при фиксированной ширине); `run()`
   (MigrationRunner.cpp:302–318) применяет неприменённые в транзакции вместе с
   записью в schema_migrations и дублёром `PRAGMA user_version = <номер файла>`
   (applyInTransaction, MigrationRunner.cpp:131–189). Для 0007_news.sql это
   значит: на свежой БД — 7-й применённый файл, user_version = 7; на существующей
   (0001–0006 + fixtures) — ровно один новый файл, user_version 6 → 7.
2. **Тесты раннера не трогал — не нужны:** `tests/unit/migration_runner_test.cpp`
   работает на собственных временных файлах (0001_test_persons.sql,
   0002_test_notes.sql — строки 82–85, 136–142, 176–177) и ассертит только их
   счётчики; реальный каталог `sql/migrations` в тестах не читается.
   `tests/security_tests.cpp:731–750` применяет реальный каталог как предусловие
   без ассертов на количество/версию — 0007 просто войдёт в «схему прод-типа»,
   которую поднимает тест.
3. **FK-гейт Р-24 — тривиально проходит:** таблица `news` не содержит внешних
   ключей (адресация аудитории — значениями audience/audience_value, словарь в
   CHECK, аналогично TEXT-подходу announcements 0003), поэтому «висячих ссылок»
   от неё быть не может; гейт `PRAGMA foreign_key_check` на каждом старте
   (MigrationRunner.cpp:364–401) перечисляет только реальные FK-нарушения —
   подтверждено фактическим прогоном (security_tests поднимает миграции 0001–0007
   реальным раннером; пустой foreign_key_check — в быстрой SQL-проверке).
4. **published_at без DEFAULT — сознательно:** постановка задаёт
   `published_at TEXT NOT NULL` без умолчания (в отличие от announcements
   0003:57, где DEFAULT strftime) — момент публикации задаёт автор/сервис, а не
   БД; быстрая проверка подтвердила: INSERT без published_at корректно
   отклоняется NOT NULL-ом.
5. **Дублирования announcements нет:** news — редакционная лента с категорией
   события/местом/временем; announcements (0003_workflow:51–58) — authored-записи
   сотрудников с JSON-аудиторией. Разные сущности, обе остаются; поведение
   объявлений не тронуто (риск Э6).

**Ошибки.**
1. В первой бытовой SQL-проверке мой второй тест-INSERT не передал
   `published_at` — sqlite честно ответил «NOT NULL constraint failed:
   news.published_at». Это ошибка тест-вставки, а не схемы (поле по постановке
   NOT NULL без DEFAULT); повторный прогон с корректными INSERT — обе вставки
   проходят. Схема не менялась.

**Решения.**
1. **Курсор «своей» ленты — по УСЛОВИЮ ВИДИМОСТИ, не по владельцу.** У
   notifications курсор перечитывается по `id AND user_id` (владелец);
   у news владельца нет (публичная сущность) — published_at строки-курсора
   перечитывается по `id AND <видимость аудитории сессии>` (NewsService.cpp,
   ветка cursor): чужая по аудитории/несуществующая строка → BadRequest
   «cursor — новость не найдена» — тот же контракт, что
   NotificationsFeedService.cpp:104-114, содержимое невидимых строк не
   раскрывается. Формат курсора и структура ответа {"news":[…],
   "next_cursor":id|null} — те же (LIMIT 20+1-детектор, kPageSize=20).
2. **Аудитория — прецедент AnnouncementsService::list.** Профиль сессии —
   тот же SELECT group_id/course; профиль есть → `(audience='all' OR
   (audience='group' AND audience_value=$g) OR (audience='course' AND
   audience_value=$c))`; профиля нет (staff, Р-6) → видит все — рабочий
   инструмент, как у объявлений (AnnouncementsService.cpp:106-141).
   audience_value — TEXT (DDL 0007), биндится СТРОКОЙ: в SQLite '1' ≠ 1
   (разные классы хранения), числовой бинд дал бы вечное «не совпадает».
   group_id/course NULL/0 → '0' не совпадает с реальными id>0 — «нет
   группы → групповые новости не видны».
3. **Аудитория новости — СКАЛЯР, ровно одна цель.** Колонки 0007 —
   audience + audience_value (одно значение), в отличие от JSON-массива
   объявлений (0003). Тело принимает те же формы, что объявления ("all" |
   массив целей — прежний парсер parseAudience), но для kind=news массив
   из >1 цели → 400 «ожидается "all" или ровно одна цель» (контроллер
   проверяет количество, сервис — kind/value). FE может переиспользовать
   знакомую форму тела.
4. **published_at = серверное «сейчас» в INSERT** —
   `strftime('%Y-%m-%dT%H:%M:%SZ','now')` в VALUES (формат DDL/фикстур;
   DEFAULT у 0007 нет — момент задаёт публикация, решение шага 1).
   id — re-select'ом по естественному ключу (category, title, body) —
   урок Э5а: не last_insert_rowid (пул соединений). Push и уведомлений
   НЕТ: news — редакционная лента (01 §4.5), таймер/дайджест Э6 не тронуты.
5. **Валидация значений — в сервисе (fail-closed), типов полей — в
   контроллере.** NewsService::publish синхронно (до БД) проверяет словарь
   category, строгий «YYYY-MM-DDTHH:MM:SSZ» event_at (приём
   RoomsService::isIsoZ: фикс-позиции + диапазоны + календарность
   обратной сборкой timegm), непустоту location, единичность аудитории —
   стиль RoomsService::create (InvalidBody синхронно). Контроллер для
   kind=news проверяет только isString у category/event_at/location.
   Словарь категорий — один на ленту и публикацию
   (NewsService::isValidCategory, словарь CHECK 0007).
6. **kind проверяется до title/body, ветка announcement не менялась.**
   Тело без kind / с kind='announcement' идёт прежним кодом байт-в-байт
   (совместимость Э6); kind вне словаря/не строка → 400 «kind — ожидается
   announcement или news». CSRF: роут прежний, POST под LoginFilter →
   CsrfCheck::verify автоматически (LoginFilter.cpp:91-99), exempt не
   добавлялись — проверено смоком (kind=news без CSRF → 403 csrf).
7. **Юнит-тесты NewsService и фикстуры news — НЕ этого шага.** Проверка
   шага по брифу: контейнерная сборка + ctest (существующие зелёные,
   security_tests явно) + смок; фикстуры news и сервисные юнит-тесты —
   следующие шаги дорожки (миграция → сервис → контроллеры → фикстуры →
   тесты). para-tests список CMakeLists не трогал (юнит-тестов сервиса
   пока нет — добавлю вместе с тестами, прецедент UserService.cpp).

**Ошибки.**
1. В первых комментариях NewsService.cpp оставил опечатки тире (« -- »
   вместо « — ») — вычищены grep'ом до сборки; на код не влияло.
   Компиляция и все прогоны — с первого раза, правок по результатам

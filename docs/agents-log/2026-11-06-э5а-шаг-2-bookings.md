## Сделано

- **`src/services/OwnershipGuard.{h,cpp}`** — белый список расширен значением `Table::RoomBookings` (enum + фиксированный SQL-литерал `SELECT user_id FROM room_bookings WHERE id = $1` + метка лога) — предусмотренный механизмом способ («новый path-id объект добавляется одним значением enum и одной SQL-строкой», шапка OwnershipGuard.h); логика guard'а не менялась.
- **`src/services/RoomsService.{h,cpp}`** — вся SQL бронирования:
  - `create()` — валидация строгого ISO «…Z» (`isIsoZ`, длина 20/T/Z/календарная дата/час≤23, `ends_at > starts_at`) → `InvalidBody` (400); `roomById` → NotFound/404; серверная проверка пересечений активных броней комнаты (`status='booked'`, idx_bookings_active): пересекающаяся бронь с тем же `starts_at` → `SlotTaken` (400 «двойная бронь», это же ловит UNIQUE), частичное перекрытие → `Conflict` (409 «только что заняли» — случай FE-сетки 03 §4.9.5); касания границ полуинтервалов ([10:00,11:00) и [11:00,12:00)) не пересекаются; INSERT со статусом-литералом `'booked'`; **исключение БД на INSERT → SlotTaken/400** (гонка UNIQUE, постановка шага 2); id созданной — детерминированным SELECT по (room_id, starts_at, status='booked') вместо last_insert_rowid (пул соединений);
  - `myBookings()` — свои активные (`status='booked'`) по `idx_bookings_user`, JOIN rooms (имя/корпус), фильтр `upcoming` (`ends_at >= nowIso`, две SQL-строки с общими колбэками — паттерн ApplicationsService::list), nowIso передаёт контроллер (SessionService::utcNow);
  - `cancelById()` — условный UPDATE `booked→cancelled` (строка НЕ удаляется — история целa): affectedRows>0 → `Canceled` (204); 0 строк → SELECT по PK различает `NotFound` (404) и `NotActive` (409, повторная отмена/блокировка); fail-closed Error.
- **`src/controllers/RoomsCtrl.{h,cpp}`** — тонкий: `POST /v1/rooms/{id}/bookings` (JSON-тело: отсутствует/не строки → 400; Created → 201), `GET /v1/room-bookings` (`?upcoming=1`, иное значение → 400 — стиль overdue), `DELETE /v1/room-bookings/{id}` — **OwnershipGuard::check(Table::RoomBookings) ДО любых данных** (правило код-ревью; Own → cancelById → 204, Forbidden → 403 «Доступ только к своим данным» — дословный пример 02 §5.1, NotFound → 404, Error → 500); повторный DELETE своей отменённой → 409 `invalid_status_transition` (в духе Э5).

## Находки шага

1. **Повторение урока Э2 (двойной move в цепочке `>>`)** — на этот раз поймано тестом триггера: в `create()` success-ветка INSERT захватывала `cb = std::move(cb)`, error-ветка строилась ПОСЛЕ и копировала уже пустой `std::function` → `bad_function_call` на error-пути (SIGABRT в юнит-тесте «исключение БД на INSERT»). Тот же латентный дефект найден ревизией в `slots()` (error-ветка выборки брони дня — тестом шага 1 не покрывался: fail-closed-тест бьёт в более раннюю ветку roomById) и в `cancelById()`. Правило закреплено комментариями: **каждая ветка цепочки копирует cb (стреляет ровно одна)**; все цепочки RoomsService переведены на копии.
2. **`id` созданной брони** — не `last_insert_rowid()` (пул соединений), а SELECT по (room_id, starts_at, status='booked'), единственность обеспечивает idx_bookings_active.
3. Юнит-тесты шага 2 пишутся с учётом фикстурных броней шага 1 (у Ани активна 06.11 14:00) — первые ожидания «0/1 активных» не учитывали их, исправлены по фактической семантике (2 активных у Ани), это ожидаемое поведение, не баг.

## Что сделано

Маппинг Verdict → HTTP (02 §6.3/§5.1): `Own` → 200 JSON, `NotFound` → 404 `{"error":{"code":"not_found","message":"Запись не найдена"}}`, `Forbidden` → 403 `{"error":{"code":"forbidden","message":"Доступ только к своим данным"}}` (формулировка — дословный пример из 02 §5.1), `Error` → 500 `internal` (fail-closed — ошибка БД не превращается в разрешение). **Владение проверяется ровно один раз**: выборка после Own — по PK БЕЗ `user_id`-условия (постановка шага: «не дублируй проверку владения SQL-условием мимо guard»; дубликат дал бы вторую, рассинхронизированную точку решения о доступе). Роут `/v1/grades/{id}` не конфликтует со статическим `/v1/grades/summary`: статический сегмент router'а Drogon приоритетнее `{id}` — сверено E2E (summary отвечает 200 сводкой, а не 403/404).

## Ошибки ИИ, пойманные и исправленные в ходе

1. **Неквалифицированное `OwnershipGuard` в тесте**: файл имел `using para::GradesService;`, но не для guard'а — `error: 'OwnershipGuard' does not name a type` (10 ошибок компиляции); поймано сборкой контейнера, исправлено добавлением `using para::OwnershipGuard;`. Попутно подтверждено, что ctest при не собравшемся бинарнике молча гоняет СТАРЫЙ (пройденный) — сборку проверять до ctest, не после.

## Сделано

- **`src/services/RoomsService.{h,cpp}`** — `block(db, roomId, staffUserId, startsAt, endsAt, reason, cb)`: валидация строгого ISO «…Z» (`isIsoZ`, ends > starts) → `InvalidBody`/400; `roomById` → `NotFound`/404; **атомарная транзакция** (`newTransactionAsync`, паттерн AppWorkflow::apply) из линейной цепочки: 1) INSERT..SELECT уведомлений по ЕЩЁ активным броням, пересекающим интервал (по одной на каждую снятую строку; type `'schedule'` — словарь CHECK 0004 `('schedule','deadline','application','announcement')`; deep_link `/room-bookings` — экран «Мои брони»); 2) UPDATE тех же строк `booked→cancelled` (строки сохраняются — история; affectedRows = счётчик снятий для тела); 3) INSERT строки блокировки `status='blocked'` (user_id = staff); 4) `last_insert_rowid()` на соединении транзакции → id; **результат отдаёт `setCommitCallback`** — ответ клиенту не опережает фиксацию. Любая ошибка шага → rollback + Error/500 (fail-closed).
- **Когерентность блокировки с шагами 1–2** (без неё блокировка деканата нерабочая):
  - `create()`: после проверки активных броней — проверка `'blocked'`-пересечений → новый исход `Blocked` → контроллер отвечает **409 `blocked`** «Интервал заблокирован деканатом» (UNIQUE частичный индекс blocked-строки не защищает — единственная линия проверки);
  - `slots()`: сетка строится UNION ALL двух статус-веток (`'booked'` — SEARCH по idx_bookings_active, `'blocked'` — SCAN единичных строк; общий `IN` ломал частичный индекс целиком — проверено EXPLAIN на шаге 1); заблокированный слот — **«booked» для всех** (это не «ваша бронь»: отменить её через DELETE брони нельзя — NotActive/409 с шага 2);
  - выборка `'blocked'`/снятие активных броней — фиксированные SQL-литералы CHECK 0005, не пользовательский ввод.
- **`src/controllers/RoomsCtrl.{h,cpp}`** — `POST /v1/staff/rooms/{id}/block` под **LoginFilter + StaffFilter** (в METHOD_LIST фильтры после LoginFilter — роль из сессии, 02 §6.3 RBAC): JSON-тело `starts_at, ends_at, reason` (02 §5.2), отсутствие/пустой reason → 400 bad_request; Created → 201 `{id, room_id, room, starts_at, ends_at, status:"blocked", reason, cancelled}`; InvalidBody → 400; NotFound → 404; Error → 500. OwnershipGuard сознательно не вызывается — аудитория общий ресурс, блокирует сотрудник (как staff-очередь Э5); в шапке зафиксировано: 409 контракта block (02 §5.2) в текущем сценарии не возникает — блокировка СНЯТАЕТ пересекшиеся брони, а не отклоняется (01 §5.10).

## Находки шага

1. **Self-reference цикл в рекурсивной цепочке транзакции** — первая редакция block() использовала рекурсивный шаг (`shared_ptr<std::function>` захватывал сам себя): замыкание никогда не уничтожалось → tx не освобождала соединение (connection_number=1) → **E2E зависла на первом же запросе после блокировки**. Лечение: линейная цепочка из 3 SQL + rowid-SELECT (INSERT..SELECT уведомлений до UPDATE-снятия — предикат один и тот же на одном соединении транзакции).
2. **Ответ до коммита** — `fire(Created)` внутри колбэка последнего SELECT отдавал 201 ДО коммита деструктором tx: sqlite-SELECT сразу после ответа читал неснятую бронь. Лечение — `tx->setCommitCallback` (паттерн AppWorkflow::apply, v1.9.14: после rollback commit-callback не стреляет; once-ограничитель страхует оба пути).
3. **Вложенный захват локалов функции** — вложенная лямбда может захватить локал функции только если промежуточные лямбды его тоже захватили (`kInsertBlockSql`/`blockId` добавлены во все промежуточные списки) — поймано компилятором.
4. **Коллизия `Result`** (урок шага 2 Э5а) — в block() лямбды написаны с полностью квалифицированным `const drogon::orm::Result&`.
5. Юнит- и E2E-ожидания дважды не учитывали фикстурные брони шага 1 (у Ани активна 06.11 14:00) — исправлены на фактическую семантику; приёмочная цепочка гейта должна это учитывать (после блокировки 13.11 у студента остаётся 1 активная фикстурная бронь).

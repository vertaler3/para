## Шаг 1 — PUT /v1/applications/{id}: submit:true переводит draft в submitted (8.i)

**Постановка.** Расширить PUT /v1/applications/{id}: опциональное поле `submit:true` у заявки в статусе draft переводит её в submitted — через автомат (AppWorkflow: событие draft→submitted С ДАТОЙ), ответ — карточка заявки с новым статусом (200). PUT с submit на НЕ-draft → 409 invalid_status_transition (как сейчас); чужая заявка → 403 (OwnershipGuard ДО всего). `submit:false`/отсутствует — прежнее поведение сохранения черновика байт-в-байт. Валидация полей черновика при submit — по контракту автомата (обязателен ли состав — решение в журнал). 02 §5.2 — обновить строку PUT этим же коммитом. Живой смок (рецепт digest.liveServerRecipe): draft → PUT submit:true → 200 submitted + событие с датой (SELECT дословно в журнал); submitted → PUT submit → 409; чужая → 403.

**Решения.**

3. **payload_json остаётся обязательным и при submit:true**: FE подаёт форму целиком (автосохранение уже шлёт payload), отсутствие поля → 400 как прежде; «submit:false/отсутствует — байт-в-байт» сохранено (ветка без submit не менялась).
4. **Сообщение 409 раздвоено по ветке, код — прежний:** invalid_status_transition в обоих случаях (совместимость FE/гейтов), текст «Подать…»/«Править…» честнее отражает операцию.

## Шаг 2 — GET /v1/ics/token: статус подписки (8.ii)

**Постановка.** GET /v1/ics/token (LoginFilter): 200 `{"token":…,"created_at":…}` если активный токен есть; 404 not_found (формат 02 §5.1) если токена нет или он отозван. POST — прежняя ротация 201, DELETE — прежний отзыв 204 (НЕ менять; Р-25 — 201 подтверждён). Токен в ответе — тот же, что отдаёт существующий ICS-фид (единый источник в сервисе). 02 §5.2 — добавить строку GET /v1/ics/token этим же коммитом. Живой смок: до POST → 404; POST → 201; GET → 200 с token/created_at (дословно); DELETE → 204; GET → 404.

**Что сделал.**
- `src/services/IcsService.h/.cpp` — новый `activeToken(db, userId, cb)`: `SELECT token, created_at FROM ics_tokens WHERE user_id = $1 AND revoked = 0` — тот же источник, что у фида `calendarByToken` (строка с `revoked = 0`); пустая выборка → `found=false` (контроллер 404), ошибка БД → `ok=false` (500). Структура `ActiveToken` зеркалит `Calendar` (ok/found + данные).
- `src/controllers/IcsCtrl.h/.cpp` — маршрут `ADD_METHOD_TO(IcsCtrl::tokenStatus, "/v1/ics/token", Get, "LoginFilter")` (сессия обязательна; GET не state-changing — CSRF не требуется, Э8); `tokenStatus`: 200 `{token, created_at}` при found, 404 `not_found` «Подписка не найдена» иначе — формулировка и код ошибки те же, что у публичного `getCalendar` (единый формат 02 §5.1), 500 при ошибке БД. POST/DELETE не тронуты — байт-в-байт.
- `tests/unit/ics_service_token_test.cpp` — новый TEST_CASE «activeToken — статус подписки»: нет строки → not found; после createToken → found с тем же токеном, created_at ISO UTC 20 симв.; ротация → activeToken отдаёт уже НОВЫЙ токен (источник один); отзыв → not found; чужая подписка (user 3) не затронута; user 42 без строки → not found.
- `docs/02-техническое-решение.md` §5.2:578 — новая строка `GET | /v1/ics/token | Статус подписки для блока профиля: активный токен и дата его создания (тот же токен, что в приватной ссылке /ics/{token}; 8.ii) | — | 200 {token, created_at} · 404 (токена нет или отозван)` — сразу после DELETE-строки ICS-блока; POST 201 / DELETE 204 не менялись (Р-25).

**Решения.**
1. **404 (не 200 с `{"active":false}`)** — «нет подписки» семантически «нет объекта»: подписка-ресурс отсутствует, зеркалит 404 публичного фида у отозванного токена. Постановка шага фиксирует именно 404/200.
2. **Сообщение 404 — то же, что у фида** («Подписка не найдена», код `not_found`): не раскрывает, отозван токен или никогда не существовал (02 §5.1 — без лишних деталей), один текст во всём ICS-контроллере.
3. **Единый источник не «копируется», а переиспользуется:** activeToken и фид читают одну и ту же строку `revoked = 0` — GET-статус не может разойтись с фидом; при ротации (POST) GET сразу отдаёт новый токен (проверено юнит-тестом и живым смоком).
4. **GET не расширяет CSRF-контур:** double-submit (cookie csrf + X-CSRF-Token) — только на state-changing POST/PUT/DELETE (Э8); GET под LoginFilter — чтение своего ресурса.
5. **Счётчики AGENTS §6 не трогаю** — обновит закрывающий шаг этапа чистым прогоном с `--build` (как в шаге 1).

**Ошибки.**
1. В живом смоке финальный контрольный SELECT упал с SyntaxError python (кавычка внутри `python -c` вокруг «…») — выведен после ВСЕХ проверок смока, на коды/тела ответов не повлиял; состояние БД (revoked=1 после DELETE) покрыто юнит-тестом. Повтор контейнера ради одного SELECT не делал — /tmp БД контейнера уже удалена (--rm).

## Шаг 3 — schedule: building/prev_building у событий (8.iv)

**Постановка.** schedule-ответы (today/week/changes) дополняются полем `building` у события: JOIN rooms по room (TEXT-ссылка), rooms.building_id JOIN buildings → имя корпуса («Корпус Б»); для prev_room — `prev_building` (аналогичный JOIN; prev_room может быть NULL → prev_building null). Миграция НЕ нужна (существующие таблицы). Отсутствующая комната (room без строки rooms) → building null, БЕЗ 500 — fail-open здесь уместен (справочные данные), решение в журнал. Обновить юнит-тесты ScheduleService (поля building/prev_building — в существующие кейсы). Живой смок: /v1/schedule/today → у событий с room есть building (дословный фрагмент JSON); событие с prev_room → prev_building. Коммит «э7-be: шаг 3 — schedule: building/prev_building у событий (8.iv)».

**Что сделал.**
- `src/services/ScheduleService.cpp` — `kSelect` (одна для today/week/changes/eventsByTeacher/eventsOnRange) += два столбца и две пары LEFT JOIN: `LEFT JOIN rooms r ON r.name = e.room → LEFT JOIN buildings rb ON rb.id = r.building_id` → `rb.name AS building`; симметрично `pr/pb` по `e.prev_room` → `pb.name AS prev_building`; `eventJson` — `e["building"]`/`e["prev_building"]` через `optString` (NULL → null). Прежние поля формы события не менялись — только добавление (совместимость FE; IcsService::eventItem читает `room`/`prev_room` — не тронуты).
- `tests/unit/schedule_service_test.cpp` — схема Fixture += срез `buildings`/`rooms` из фикстур v2 (обе таблицы 0006/0005: все шесть аудиторий демо-недели — 1201/2109 → Корпус Б, 2210/3024/3105/4210 → Корпус А); CHECK `building`/`prev_building` в существующих кейсах today (отмена 7: 2109 → «Корпус Б» по обеим ссылкам; семинар 8: 1201 → «Корпус Б», prev null), week (id 1/10; fail-open: дополнение теста id 11 ауд. 4205 и id 20 ауд. 5102 БЕЗ строк rooms → building null, события в выборке), changes (moved 5: 4210/3024 — обе «Корпус А», перенос внутри корпуса; cancelled 7; substituted 11 — 4205/3201 → null/null). Новых TEST_CASE нет — только CHECK в существующих.
- `tests/unit/people_service_test.cpp` — первая сборка вскрыла: PeopleService::schedule переиспользует `ScheduleService::eventsByTeacher`/`eventsOnRange` (общий kSelect), а в схеме теста не было rooms/buildings → «no such table: rooms» → Error, 2 кейса красные. Схема дополнена тем же срезом (аудитории 1201/3024 этого теста) + CHECK building («Корпус А»)/prev_building (null) в кейсе занятий преподавателя.
- `docs/02-техническое-решение.md` §5.2:571-573 — строки today/week/changes дополнены корпусом события (building JOIN'ом; аудитория без строки rooms → null; у переноса — prev_building); прежние поля формы события в документе не тронуты.

**Решения.**
1. **Fail-open для отсутствующей комнаты (постановка):** LEFT JOIN — комната без строки rooms даёт building null, событие НЕ исчезает из выборки и НЕ даёт 500.

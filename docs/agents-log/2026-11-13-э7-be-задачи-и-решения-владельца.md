## Шаг 1 — PUT /v1/applications/{id}: submit:true переводит draft в submitted (8.i)

**Постановка.** Расширить PUT /v1/applications/{id}: опциональное поле `submit:true` у заявки в статусе draft переводит её в submitted — через автомат (AppWorkflow: событие draft→submitted С ДАТОЙ), ответ — карточка заявки с новым статусом (200). PUT с submit на НЕ-draft → 409 invalid_status_transition (как сейчас); чужая заявка → 403 (OwnershipGuard ДО всего). `submit:false`/отсутствует — прежнее поведение сохранения черновика байт-в-байт. Валидация полей черновика при submit — по контракту автомата (обязателен ли состав — решение в журнал). 02 §5.2 — обновить строку PUT этим же коммитом. Живой смок (рецепт digest.liveServerRecipe): draft → PUT submit:true → 200 submitted + событие с датой (SELECT дословно в журнал); submitted → PUT submit → 409; чужая → 403.

**Что сделал.**

- `src/services/ApplicationsService.h` — `parsePayloadJson/TextSpec` заменены на `parseUpdate/UpdateSpec` (payload_json — обязательная строка с валидным JSON; `submit` — опциональный bool, не-bool → 400); сигнатура `updateDraft` += `(bool submit, int64_t authorId)`; док-комментарии шапки и метода дополнены контрактом 8.i.
- `src/services/ApplicationsService.cpp` — `parseUpdate`; в `updateDraft` новая submit-ветка: `AppWorkflow::apply(db, id, "submitted", nullopt, authorId, cb, afterEvent-хук)`, хук пишет payload той же транзакцией (`kUpdateSubmitPayloadSql` — UPDATE только по PK: статусное условие уже отработал автомат условным UPDATE'ом; сбой хука → `fail()` → откат статуса/события/payload). InvalidTransition автомата → `NotDraft` (контроллер — прежний 409 invalid_status_transition), NotFound → 404, Applied → карточка по PK (паттерн staffChangeStatus). - `src/controllers/ApplicationsCtrl.cpp` — `parseUpdate` вместо `parsePayloadJson`; в OwnershipGuard-лямбду захвачен `userId = session.userId` (автор события подачи — владелец); сообщение 409 выбирается по ветке: submit → «Подать можно только черновик заявки», иначе прежнее «Править можно только черновик заявки» (код ошибки и статус прежние — invalid_status_transition/409). Guard — по-прежнему ДО разбора тела и до статуса (чужая → 403 в любой ветке).
- `tests/unit/applications_service_test.cpp` — хелпер `putOf` += параметры `submit=false, author=4` (существующие кейсы — прежние вызовы, семантика не изменилась); 3 новых TEST_CASE: (1) подача черновика — Ok/submitted/payload обновлён/событие draft→submitted с `at` (20 симв.) и author_id=4; повторный submit → NotDraft, событие одно, payload не перезаписан; submit:false на submitted → NotDraft; (2) submit на терминальных (issued/cancelled) → NotDraft, payload не тронут, событий 0; (3) parseUpdate: нет payload_json → 400, submit не-bool → 400, submit:false/true, не-JSON → 400.
- `docs/02-техническое-решение.md` §5.2:585 — строка PUT дополнена: назначение включает `submit:true` (draft → submitted через автомат + событие с датой, Р-29/8.i), параметры `body: payload_json, submit (опц., bool)`, ответы 200 (карточка; при submit — со статусом submitted) · 400 · 403 · 404 · 409.

**Решения.**
1. **Состав payload при submit НЕ валидируется** (вопрос постановки): 02 §6 требований к полям submitted не фиксирует, POST submit:true исторически допускает `'{}'` (DEFAULT DDL 02 §4.1) — контракты POST- и PUT-подачи совпадают, единственный инвариант «payload_json — валидный JSON» (400 иначе). Зафиксировано в Р-29.
2. **Переход — ТОЛЬКО через AppWorkflow::apply** (не ручной UPDATE+INSERT): гарантия события с датой `at` (DEFAULT DDL), защита от гонок условным UPDATE по from-статусу, единая матрица (draft→submitted уже в 16 парах, 05 §3 Э5). Payload пишется хуком afterEvent В ТОЙ ЖЕ транзакции — сбой любого шага откатывает всё.
3. **payload_json остаётся обязательным и при submit:true**: FE подаёт форму целиком (автосохранение уже шлёт payload), отсутствие поля → 400 как прежде; «submit:false/отсутствует — байт-в-байт» сохранено (ветка без submit не менялась).
4. **Сообщение 409 раздвоено по ветке, код — прежний:** invalid_status_transition в обоих случаях (совместимость FE/гейтов), текст «Подать…»/«Править…» честнее отражает операцию.
5. **Р-29 записан ДО правки 02** — протокол §7.3 (риск №5 из разведки этапа).
6. **Счётчики AGENTS §6 не трогаю** — их обновляет закрывающий шаг этапа чистым прогоном с `--build` (прецедент 5.18 шаг 8).

Существующие service-проверки шагов 4/8 можно заменить HTTP-версией (сильнее). Существующий para-tests остаётся зелёным.

**Решения.**
1. **Service-level проверки шагов 4/8 (Э4/Э5а) заменены HTTP-версией** — она сильнее: та же логика под настоящими LoginFilter/StaffFilter и контроллерами, живые cookie вместо параметра user_id. Fail-closed ветка guard'а (ошибка БД → Error → 500) не потеряна — она покрыта в para-tests (tests/unit/ownership_guard_test.cpp, TEST_CASE «ошибка БД → Error, fail-closed», строка 143).
2. **Пароль тестовых сессий** (AGENTS.md §5.2, прецедент изъятия демо-пароля): демо-пароль жюри тесту НЕ известен; единый тестовый пароль генерируется в памяти процесса (std::random_device), argon2id-хэши трёх фикстурных аккаунтов (anya.demo id 1, oleg.demo id 2, dean.demo id 5) выставляет сам тест через PasswordHasher::hash() поверх временной БД; в репозитории и логах его нет.
3. **Буквальная пара §9.3 Аня/Олег восстановлена и для шага 4** (вопрос из digest Э4 «возврат к буквальной паре — вопрос Э8»): фикстуры v2 дают Ане пустую успеваемость (предусловие С5.6 демо-сценария), поэтому ТЕСТОВАЯ БД добавляет Ане ровно одну оценку — иначе «чужой id_grade_ани» не определён; на демо-БД фикстуры не влияют.
4. **Проверяются не только коды, но и ФАКТЫ неизменности** (чужая попытка ничего не изменила): уведомление Ани остаётся в unread=1 после чужого 403; бронь Ани остаётся «booked» в /v1/room-bookings после чужого DELETE; после своего 204 объекты уходят из unread/списка.
5. **Контроли против ложного зелёного:** свой объект своей сессией → 200/204 (403 — именно про «чужое», не про сломанный роут); dean.demo на /v1/staff/* → 200 (403 студента — именно RBAC); /v1/me с cookie → 200 (401 без cookie — именно отсутствие сессии); три разных токена сессий; Set-Cookie несёт HttpOnly; Secure; SameSite=Lax.
6. **CSRF/заголовки в шапке файла честно:** сейчас CsrfCheck и CSP/nosniff сервером НЕ реализованы, но ни один шаг §9.3 от них не зависит — на шаге 1 все проверки зелёные; когда CsrfCheck появится (шаги 2–3 Э8), state-changing проверки этого файла ДО синхронизации (cookie csrf + заголовок/поле) будут ожидаемо красные — норма; полное озеленение — к шагу 5 Э8, синхронизация файла входит в шаг 3.
7. **429-тест НЕ ждёт блок 15 с** — проверяется сам факт 429 + Retry-After на 4-й попытке + изоляция лимитера (другой логин не заблокирован); логин-цель «limiter-check.demo» не существует в фикстурах — это штатная ветка AuthCtrl (неудача учитывается и для несуществующего логина; mirrorFailedAttempts — UPDATE-only).

**Ошибки.** (все пойманы и исправлены в этой же сессии, честно)
1. **drogon API: `ReqResult::Success` не существует** — в v1.9.14 это `ReqResult::Ok` (HttpTypes.h:205); первый прогон не собрался (1 ошибка компиляции).
2. **Клиентский JSON-запрос уходил без content-type-энума**: `addHeader("Content-Type")` не заполняет `contentType_` у исходящего запроса — сервер отвечал 400 на все логины («Ожидается JSON с полями login и password»), 9/58 на первом прогоне. Лечено каноничным `req->setContentTypeCode(drogon::CT_APPLICATION_JSON)` (как newHttpJsonRequest). Серверная сторона при этом была здорова — проверено curl'ом к живому контейнеру para (401 invalid_credentials).
3. **`getHeader("Set-Cookie")` у клиентского ответа ПУСТОЙ**: клиентский парсер drogon превращает `set-cookie` в объекты `cookies_`, не в `headers_` (HttpResponseImpl.cc:998) — три логина дали 200, но токены не извлекались → все авторизованные проверки ходили 401 (22/50 на втором прогоне). Лечено `resp->getCookie("para_session")` → `Cookie::value()/isHttpOnly()/isSecure()/sameSite()==kLax` (проверки флагов стали точнее, чем по строке).
4. **`GET /ws` без upgrade-заголовков → 404 роутера**, не ответ приложения: drogon матчит WS-роуты только для upgrade-запросов. Тест шлёт настоящий RFC 6455 handshake (Upgrade: websocket + Sec-WebSocket-Key) БЕЗ cookie → 401 до апгрейда — это и есть контракт Э6 («wsБезCookie → 401»). Отдельный HttpClient для handshake: после upgrade-запроса соединение keep-alive общего клиента закрывается сервером (следующий запрос — «транспортная ошибка», поймано на прогоне).
5. **«corrupted double-linked list» на выходе первого прогона**: HttpClient освобождался ПОСЛЕ остановки обоих event loop'ов (глобальная g_client деструктурируется после локалов main). Лечено RAII-порядком: ClientReset (сброс g_client, пока оба цикла живы) → clientLoop → ServerGuard (app().quit() + join). На финальном прогоне коррупции нет.
6. **Тривиально «зелёные» факты-проверки**: «строка ушла из unread / брони» проходили и при упавшем предшествующем запросе (объект и так отсутствовал) — факты-проверки сделаны условными: оцениваются только при подтверждённом коде предшествующего шага (403/204).
7. **`ClientReset() = default`** пришлось объявить явно: удалённый copy-конструктор подавляет implicit default (ошибка компиляции 702:17, второй итерации).

## Шаг 2 — CSRF double-submit на state-changing (02 §6.4)

**Постановка.** Реализовать серверно: на ВСЕ state-changing POST/PUT/DELETE — проверка токена double-submit (cookie csrf + скрытое поле/заголовок, проверка в CsrfCheck, 02 §6.4 дословно); страница выдаёт токен (hidden-поле `_csrf` и/или meta для htmx); расхождение/отсутствие → 403 (для htmx — по контракту ошибок проекта). Порядок с /auth/login (сессии ещё нет) и /ws — строго по 02 §6.4, там где не задано — разумное решение + запись в журнал. Обновить static/app.js (перехватчик, добавляющий токен ко всем не-GET) и нужные views. Правки LoginFilter — BE-дорожка (Р-20 дословно). CSRF-кейсы шага 1 (58/58) — остаются зелёными, CSRF-блок новый.

**Что сделал.**
- Дочитал код: полный роут-лист всех контроллеров (ADD_METHOD_TO) — state-changing роутов 15, из них 14 приватных под LoginFilter, 1 публичный (POST /v1/auth/login); /ws — GET-handshake; SSR-страницы — все GET (нативных form-POST нет: login.csp method=post перехватывается preventDefault'ом app.js, application_form/staff/map — fetch/JS); htmx в проекте ходит только GET (htmx.ajax в app.js:3692), фрагменты /schedule/segment и /staff/app-card УЖЕ требуют HX-Request с Э7 (ScheduleCtrl.cpp:381, StaffCtrl.cpp:477) — требование 02 §6.4 «HX-Request для htmx-эндпоинтов» реализовано существующим кодом.
- Создал src/filters/CsrfCheck.{h,cpp} (компонент, названный в 02 §6.4): tokenFor(session) = sha256("para-csrf-v1:"+токен сессии) → 64 hex (256 бит), детерминированный, без серверного состояния; cookieFor — Cookie csrf: Path=/, Max-Age=TTL сессии, Secure, SameSite=Lax, БЕЗ HttpOnly (токен читает app.js — единственная cookie проекта без флага; секрет сессии HttpOnly); verify(req) — тройной инвариант «присланный (заголовок X-CSRF-Token, иначе поле _csrf) == cookie csrf == tokenFor(session)», сравнение constant-time (CRYPTO_memcmp), fail → 403 {error:{code:"csrf"}} (02 §5.1, message «страница устарела»); registerPageIssuanceAdvice() — post-handling advice: на GET с живой cookie сессии выдаёт/освежает csrf-cookie при расхождении (самовосстановление) и ставит `<meta name="csrf-token">` перед единственным `</head>` страницы (все 19 view-шаблонов включают partials/head.csp; htmx-фрагменты без `</head>` мету не получают — им не нужно).
- LoginFilter (правка BE-дорожки, Р-20): ПОСЛЕ валидации сессии, на Post/Put/Delete — CsrfCheck::verify, fail → 403. Единая точка: правило 02 §6.3 «новые приватные роуты обязаны добавляться с LoginFilter» автоматически покрывает и будущие роуты (отдельный фильтр на каждый из 15 роутов в 7 файлах дал бы дрейф).
- AuthCtrl::login: вместе с cookie сессии выдаёт csrf-cookie (addCookie(CsrfCheck::cookieFor(token,ttl)) — вторая строка Set-Cookie в ответе входа).
- main.cpp: registerPageIssuanceAdvice() — один вызов на процесс; ТОТ ЖЕ вызов добавлен в security_tests (сервер теста конфигурационно идентичен продовому — иначе страницы теста не выдавали бы токен).

Правка в рамках FE-задачи шага (постановка прямо именует app.js и views).
- views: правки НЕ потребовались — мета ставится advice'ом серверно во все страницы разом (точка выдачи едина с точкой проверки; поштучная вставка csrfToken в 24 рендер-точки 14 контроллеров с async-замыканиями дала бы широкий дифф без единого поведения). Проверка «страницы выдают токен» — grep + факт-проверка тестом (meta == cookie в теле GET /schedule).
- security_tests.cpp синхронизирован: Login несёт csrf (cookie csrf из Set-Cookie входа), get/post/del переведены на (const Login&) — post/del автоматически несут cookie csrf + X-CSRF-Token, get — НЕ несёт (GET — чтение); loginAs добавил проверки csrf-cookie (64 hex; без HttpOnly; Secure; SameSite=Lax); НОВЫЙ блок «CSRF double-submit» (10 проверок): страница выдаёт токен (meta==cookie), POST без токена → 403 csrf, неверное зеркало (заголовок ≠ cookie) → 403, ПОДДЕЛАННАЯ cookie (cookie=заголовок=мусор) → 403 (привязка к сессии), с валидным токеном → 201 (контрпример), GET без токена → 200, вход без csrf → 200 (вне CsrfCheck), logout с токеном → 200 + /v1/me → 401 (инвалидация). Шапка файла честно переписана (реализовано шагом 2; CSP/nosniff — шаг 3).
- Запись Р-23 в docs/decisions.md: signed double-submit + единая точка проверки + вход/GET вне проверки + следствие для смока AGENTS §4 (logout требует токена — строка смока обновлена; исторические смоки Э2–Э7 — датированные записи своего времени, не переписываются).

**Решения.**
1. **Токен привязан к сессии (signed double-submit, OWASP), не plain случайный.** Plain (сравнение «cookie == присланное») уязвим к подкидыванию cookie с подконтрольного поддомена — атакующий контролирует и cookie, и заголовок. Привязка sha256(токен сессии) делает подкинутую cookie бессмысленной (верное значение не вычислить — токен сессии HttpOnly), при этом серверу НЕ нужно состояние и миграция таблицы sessions (Р-23, вариант 3 отклонён). Все артефакты 02 §6.4 на месте: cookie csrf, поле/заголовок, CsrfCheck.
2. **Проверка — из LoginFilter, не отдельный фильтр на каждом роуте.** 02 §6.4 называет КОМПОНЕНТ («проверка в CsrfCheck») — он существует (класс CsrfCheck); точка вызова — LoginFilter после валидации сессии: одна точка покрывает все 14 приватных state-changing роутов и все будущие (правило код-ревью 02 §6.3), отдельная регистрация в 7 заголовках дала бы дрейф. Порядок: сессия → CSRF (CSRF без сессии бессмыслен, login-обход ниже).
3. **/v1/auth/login — вне CsrfCheck.** 02 §6.4 порядок не задаёт; до сессии токен не существует (в т.ч. привязанный). Вход защищён первым барьером того же §6.4 (SameSite=Lax) + лимитером; login-CSRF (подлог входа) — nuisance-вектор для демо-контура с одним доменом. Смок AGENTS §4 (curl без csrf) сохранён — иначе потребовалась бы правка канонических команд жюри (потрачено на Р-23 для logout — см. ниже).
4. **/ws — вне CsrfCheck (спека дословно).** «state-changing только POST/PUT/DELETE» — /ws это GET-handshake; его контракт (без cookie → 401 до апгрейда) уже закрыт LoginFilter и проверяется шагом 7 §9.3.
5. **403 для htmx — тот же единый формат 02 §5.1** ({error:{code:"csrf"}}): state-changing htmx-эндпоинтов в проекте нет (htmx ходит только GET), «content negotiation по HX-Request» в 02 §5.1 помечен «с Э2» и не реализован — отвечать всем 403 JSON по единому контракту проще и честнее, чем вводить HTML-ветку без потребителя.
6. **Выдача токена — advice'ом, не правками 24 рендер-точек.** registerPageIssuanceAdvice — одна точка на все страницы + все будущие (то же свойство «нет дрейфа», что у проверки); мету получают ровно шаблоны с </head> (19 страниц), фрагменты — нет. login.csp method=post не требует скрытого поля: form-submission перехватывается app.js (preventDefault) — все мутации идут через fetch с заголовком; поле `_csrf` принимается verify() серверно на будущие HTML-формы.
7. **logout под CSRF (state-changing POST, 02 §6.4 «ВСЕ») → смок AGENTS §4 обновлён** (строка logout с X-CSRF-Token из jar), записано в Р-23 по протоколу §7.3 (сначала decisions.md, затем AGENTS.md); OWASP прямо рекомендует защищать logout (предотвращает CSRF-разлогинивание).

**Ошибки.** (все пойманы и исправлены в этой же сессии, честно)
1. **Компоновка теста:** первая вставка `const Login anon;` встала ВЫШЕ определения struct Login → не собралось бы; перенос структуры над sendHttp до первой сборки.
2. **Компиляция CsrfCheck.cpp — две итерации:** (а) `const std::string body(...)` — insert на константе (снят const); (б) `k403Forbidden` внутри `namespace para` не резолвится без `drogon::` — квалифицировал. Первые два «58/58 зелёных» прогона были СТАРЫМ бинарём шага 1 из примонтированного build/ (цель para падала, старый артефакт оставался и запускался по `;`) — честно вычеркнуты из доказательств, вывод их не цитирует.
3. **GET /schedule в тесте → drogon-404 «Not Found»:** security_tests НЕ содержал сгенерированных CSP-шаблонов — `drogon_create_views` вызывался только для цели para; до шага 2 тест никогда не рендерил страницы (единственный заход /schedule — анонимный → 303 от фильтра ДО контроллера). newHttpViewResponse с незарегистрированным шаблоном отвечает дефолтной 404-страницей Drogon (сверено с исходником v1.9.14). Лечение: `drogon_create_views(security_tests …)` в отдельный каталог generated-security-tests (генерации para и теста не пишут в одни файлы). ## Шаг 4 — выравнивание тайминга входа (находка Э1: timing-оракул)

**Постановка.** В цепочке входа (AuthCtrl + UserService + PasswordHasher) ответ при НЕСУЩЕСТВУЮЩЕМ логине должен стоить примерно столько же, сколько при неверном пароле: сейчас `PasswordHasher::verify` (argon2id, десятки мс) вызывается только при `user.has_value()` (AuthCtrl.cpp:75-77 — короткое замыкание `&&`), то есть время ответа различает «нет логина»/«неверный пароль» (находка Э1-timing-оракул, medium, ревью шагов 4–7 Э1; тело уже одинаковое — 401 invalid_credentials, остаётся время). Правка: фиктивный прогон argon2 (та же функция, те же параметры t=2/m=19456/p=1, соль-заглушка) до ответа «неверный логин». Замерить фактически в контейнере обе ветки (несколько прогонов, среднее/разброс) — до и после правки, записать замеры в журнал. Тайминг-проверки в security_tests шага 1 НЕТ (grep по «timing|тайм» — пусто, подтверждено в этой сессии) — условий «сделать зелёной» нет, security_tests обязан остаться 108/108 (регрессионный гейт шага).

- Прочитал цепочку входа: AuthCtrl.cpp:71-93 (короткое замыкание `user.has_value() &&` на verify), PasswordHasher.cpp (argon2id, t=2, m=19456, p=1; verify = argon2id_verify), LoginLimiter.cpp (блок после 3 неудач ПОДРЯД НА ЛОГИН — протокол замера обязан это учитывать). **Решения.**
1. **Фиктивный прогон — тот же путь кода, что и реальная проверка** (`argon2id_verify` против PHC-строки с теми же параметрами и солью-заглушкой), а не отдельный «прогрев»: парсинг PHC + KDF + constant-time сравнение — идентичная стоимость с точностью до шума; 02 §6.2 (та же функция/параметры OWASP) соблюдено буквально.
2. **PHC-строка — захардкоженная константа, не ленивая инициализация**: статик с вычислением при первом вызове сделал бы ПЕРВЫЙ после старта ответ «нет логина» вдвое дороже (генерация паддинга + проверка) — оракул перевернулся бы на один запрос («медленнее = логина нет»). Константа даёт равную стоимость с нулевого запроса. Она не секрет: хэш заведомо непроверяемого паддинга «para-timing-pad» с фиксированной солью (приём OWASP «dummy verify», прецедент Django); §5.2 не нарушается.
3. **verifyDummy — в PasswordHasher, ветка — тернарник в AuthCtrl**: argon2-детали остаются в сервисе (02 §5.5 «контроллер тонкий, SQL/крипто — в сервисах»; AuthCtrl выбирает только ветку), контроллер не оброс кодом.
4. **Тайминг-порогов в юнит-тестах НЕТ** (только функциональные: false на любом пароле, не бросает): ассерт на время хрупок в CI/под эмуляцией; факт выравнивания доказан живым замером обеих веток в журнале (до/после).
5. **security_tests.cpp не менялся**: тайминг-проверки в нём не было (grep 0 вхождений — постановка условная «если есть»), а ассерт на время в HTTP-тесте был бы таким же хрупким; число проверок осталось 108/108 — регрессионный гейт шага.

**Ошибки.**
1. **Первая попытка замера ДО: ротация логинов без модуля** — `${REAL[$((i-1))]}` вместо `% 6`: попытки 7–10 уходили с ПУСТЫМ логином, пустой логин набрал 3 неудачи → 429-попытка попала в выборку (виден в выводе: CODES_REAL … 429). ## Шаг 5 — foreign_keys=ON и исправление double move cb (Э2/Э5а)

**Постановка.** (а) `PRAGMA foreign_keys=ON` на КАЖДОМ создаваемом соединении SQLite: найти ВСЕ места создания клиентов/соединений (grep по sqlite3_open, DbClient, SQLite, PRAGMA — src/, тесты, main) и включить FK на каждом; где технически нельзя — запись Р-N с обоснованием. (б) grep-аудит всех awaiting-цепочек на двойной move cb (находки Э2 и Э5а): src/services, src/controllers, src/utils по паттернам std::move с колбэками; каждую найденную двойную move исправить; аудит — в журнал. Гейт: ./build/security_tests полностью зелёный (108/108, «шаги 1–8 ПРОЙДЕН», exit 0).

**Что сделал.**

*(б) Аудит double-move — метод и результаты.*
- Грепы по src/: `std::move(cb`/`>> std::move` (по-файловый подсчёт), `cb = std::move(cb)` (все 74 вхождения — просмотрены), пары близких вхождений awk'ом. Знание механики: в цепочке `binder >> L1 >> L2` замыкания строятся слева направо (C++17: объект-выражение `tmp.operator>>` секвенировано ДО аргумента; внутренний вызов должен завершиться до результата), поэтому `cb = std::move(cb)` в первой лямбде ГАРАНТИРОВАННО оставляет второй пустой std::function — это дословно задокументированный в OwnershipGuard.cpp:59-62 урок Э2 с реальным SIGABRT. СЛЕДСТВИЕ, найденное этим аудитом: тот же дефект даёт и смешанный паттерн «первая ветка move, соседняя ветка `[cb]`-копия» — копия снимается с УЖЕ опустошённого оригинала. Дефект ≠ только «двойной move», а «move в одной ветке + любое sibling-захватывание того же cb».
- Дефекты (17 веток, 7 файлов; во всех error-ветка получила бы пустой cb → bad_function_call на первом сбое БД): UserService::findByLogin (:17/:30 — move+move) и loadProfile (:46/:62 — move+move); SessionService::create (внешняя цепочка :85/:97 move+move И внутренняя :89/:92 move+move), findValid (:113/:125), remove (:136/:137) — все move+move; StaffDashboard::build (внешняя :71+копия, внутренняя :82+копия — смешанный); AnnouncementsService::list (внешняя :108+копия, внутренняя :156+копия) и publish (внешняя :204+копия, внутренняя :210+копия) — смешанный; SettingsService::load (:43+копия) и save (:94+копия) — смешанный; ReminderService::basicDeadlineRound (:167+копия) и personalReminderRound (:195+копия) — смешанный; ScheduleChangeService::apply — три цепочки (select event :241+копия-в-:535, teacher :524-цепочка +копия-в-:529, recipients :330+копия-в-:511) — смешанный. Всё исправлено по канону Э5а (RoomsService — эталон): копия `[cb]` в КАЖДОЙ ветке цепочки (стреляет ровно одна); одноветвевые move (токен сессии, единственный continuation) оставлены.
- Чисто (проверено пофайльно, правок не требует): контроллеры — 0 цепочек `>>` (grep DrogonDbException/`<<` по src/controllers — пусто), все cb уходят ОДНИМ аргументом в один сервисный вызов (single-successor — move безопасен); OwnershipGuard, GradesService, ScheduleService (groupOfUser copy-copy; остальные — односукцессорные continuation), RoomsService (весь copy — фикс Э5а), ApplicationsService (copy + fire/once-паттерн транзакций), NotifyDispatcher (insert-цепочка copy+copy, комментарий урока Э2), DashboardService (state->cb — единственный владелец, fire-once через pending-счётчик), Canteens/Map/People/Gradebook/Rating/Ics/Library/AppWorkflow/NotificationsFeed — все sibling-ветки `[cb]`-копии.

CMakeLists.txt: UserService.cpp добавлен в список para-tests (раньше сервис не линковался тестами — user-сервис тестов не имел).

*(а) FK — инвентаризация точек создания соединений и правки.*
- Grep по `sqlite3_open|getDbClient|createDbClient|newSqlite3Client|PRAGMA|initialization_queries` (src/, tests/, config.json, main): точки — пул «para» из config.json (прод); тест-конфиг security_tests (writeTestConfig); сидер security_tests (RawDb, sqlite3_open_v2); 16 клиентов юнит-тестов `newSqlite3Client("filename="+dbPath, 1)`; raw-соединения MigrationRunner (:27), хелперы/верификаторы юнит-тестов; main.cpp клиент НЕ создаёт (берёт по имени из конфига).
- Механика Drogon проверена по ИСХОДНИКАМ v1.9.14 в контейнере (/install/drogon/orm_lib/src/sqlite3_impl/Sqlite3Connection.cc): initializationQueries_ исполняются через sqlite3_exec на КАЖДОМ новом соединении (внутри runInLoop сразу после sqlite3_open; ошибка query → соединение закрывается); DbClientManager.cc:147 передаёт их из config. Перегрузка `newSqlite3Client(connInfo, connNum, initializationQueries)` существует; connection-string парсит только ключ filename — init-queries передаются именно третьим аргументом.
- Правки: config.json initialization_queries += «PRAGMA foreign_keys=ON;» (с комментарием); writeTestConfig security_tests — то же (прод-паритет); RawDb сидера — pragma после открытия (сид FK-согласован: UPDATE users, INSERT grades с существующей discipline_id=1, INSERT notifications с существующим user_id); 16 юнит-тестов — третий аргумент `{"PRAGMA foreign_keys=ON;"}`.
- MigrationRunner — Р-24 (docs/decisions.md): enforcement на его соединении НЕ включается — (1) pragma внутри его транзакций — no-op (SQLite; Р-13), (2) schema-фаза по руководству SQLite идёт с FK OFF (DROP/пересоздания с сылками → implicit DELETE), (3) порядок вставок fixtures.sql не обязан быть FK-упорядоченным. КОМПЕНСАЦИЯ КДОМ: в MigrationRunner::run добавлен гейт `PRAGMA foreign_key_check` на каждом старте (работает при любом enforcement; первая висячая ссылка → MigrationError со строкой в логе; итоговая строка раннера дополнена «foreign_key_check — ok») — несогласованная БД приложение НЕ поднимет.
- Raw-хелперы/верификаторы юнит-тестов — сознательно БЕЗ FK (не прикладной SQL; часть намеренно вносит сломанные данные для fail-closed тестов; READONLY не пишет) — зафиксировано в Р-24 как «сознательно не делается», не «невозможно».
- ПРЯМАЯ ВЕРИФИКАЦИЯ enforcement (одноразовая программа в контейнере, вне репо; линковка — точными библиотеками link.txt цели para): клиент `newSqlite3Client(..., {"PRAGMA foreign_keys=ON;"})` → `PRAGMA foreign_keys` = **1**, INSERT в child с pid=999 (родителя нет) → **«FOREIGN KEY constraint failed»**; отрицательный контроль (без init-query): `foreign_keys=` **0**, тот же INSERT ПРОШЁЛ — дословное воспроизведение находки Э1 и доказательство, что enforcement включает именно init-query.

**Решения.**
1. «Дефект» трактован по уроку Э2, а не по букве «двойной move»: move в одной ветке цепочки + любой sibling-захват того же cb = пустая функция в sibling → исправлены и смешанные паттерны (их большинство), не только move+move. Канон — копия cb в каждой ветке (RoomsService, Э5а).
2. Односукцессорные move НЕ тронуты (контроллеры → один сервисный вызов; сервис → один continuation): ровно один потребитель, move безопасен и дешевле копии; править их — шум диффа без поведения.
3. FK — через init-queries Drogon (per-connection при каждом создании/переподключении), а не через разовые execSql: пере-подключение пула не теряет enforcement.
4. MigrationRunner: гейт foreign_key_check вместо enforcement — фиксирует «данные согласованы» КАЖДЫЙ старт (раньше это была разовая ручная проверка из Э6а/Э6б), fail-loud на несогласованных фикстурах; Р-24 по протоколу §7.3 (отклонение от «включить на каждом» — обосновано).
5. Регрессионный тест на error-ветки — в auth_unit.cpp (сервисы входа/сессии — владельцы исправленных цепочек; fail-closed прецедент OwnershipGuard Э2), без порогов на время/поведение event loop.

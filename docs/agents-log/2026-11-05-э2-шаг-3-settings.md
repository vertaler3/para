# Журнал ИИ-сессии — Э2, шаг 3: настройки уведомлений GET/PUT (BE-дорожка)

- **Дата:** 05.11.2026 · **Дорожка:** BE · **Инструмент:** агентская сессия в составе workflow шагов Э2
- **Промпт (суть):** «Прочитай AGENTS.md (раздел 5), гайд-бэкенд §4 (Э2), 02 §5.2, §4.1 (settings в миграции 0004), §5.1. Шаг 3 Э2: тонкий контроллер GET/PUT /v1/notifications/settings, вся логика и SQL — в сервисе; PUT меняет строку settings ТОЛЬКО текущей сессии (user_id из тела игнорируется); GET при отсутствии строки — дефолты по 02 §5.2; валидация theme (light/dark по токенам 03) и валидный JSON в *_json → 400 в формате 02 §5.1; страница /profile не обязательна; юнит-тест SettingsService: дефолты, UPSERT перезаписывает, чужая строка не затрагивается; коммит».

## Что сделано

- `src/services/SettingsService.{h,cpp}` — вся логика и SQL: `load()` — параметризованный SELECT строки settings по user_id, при отсутствии — дефолты ровно из DEFAULT миграции 0004 (чтение строку не создаёт — ленивое создание при первом PUT); `save()` — UPSERT `INSERT … ON CONFLICT(user_id) DO UPDATE SET … = excluded.*` (SQLite ≥3.24; в контуре 3.37+); `applyPatch()` — частичное обновление (поле без значения в теле не меняется — так закрывается шаг онбординга С5 одиночным `{"onboarding_json": …}`), валидация: theme ∈ {light, dark, system} (токены 03 §2: системная по prefers-color-scheme + ручной переключатель; дефолт `system` — из DDL), quiet_hours_json/onboarding_json — строки с валидным JSON; ошибки — код `bad_request` + message для формата 02 §5.1; `toJson()` — вложенные JSON-значения для quiet_hours/onboarding. user_id записи приходит только из сессии; user_id из тела не читается вовсе. В лямбдах `load/save` колбэк **копируется** в обе ветки (result/exception) — урок шага 1 (double-move давал bad_function_call на error-пути); ошибка БД в load — fail-closed (дефолты), в save — cb(false) → 500.
- `src/controllers/SettingsCtrl.{h,cpp}` — тонкий: GET (атрибуты сессии → load → JSON) и PUT (JSON-тело → applyPatch → 400 или save → 200 с итоговой записью); оба под LoginFilter (без cookie — 401 от фильтра); path-id нет — OwnershipGuard не применим (правило — для эндпоинтов с {id} в пути); страница /profile не нужна (JSON самодостаточен) — views/ и static/ не тронуты.
- `tests/unit/settings_service_test.cpp` — 4 тест-кейса на временной SQLite (схема — колонки settings из миграции 0004 без FK): дефолты при отсутствии строки (+чтение не создаёт строку), UPSERT перезаписывает без дублей (count==1), чужая строка не затрагивается (два пользователя, save первого не меняет второго), applyPatch: theme=pink → отказ, невалидный JSON → отказ, частичное обновление не трогает остальные поля, user_id из тела игнорируется (userId остаётся от сессии).
- `CMakeLists.txt` — SettingsCtrl.cpp в `para`; SettingsService.cpp в `para` и `para-tests`; тест в `para-tests`.

## Ошибки/уточнения ИИ, учтённые в ходе

- Забыт include `services/SessionService.h` (SessionInfo — атрибут LoginFilter) в SettingsCtrl — поймано компиляцией контейнера, исправлено.
- Формулировка ask «открытые шаги онбординга С5» vs комментарий DDL/02 §4.1 «закрытые шаги чеклиста онбординга С5 (4 шага)»: дефолт одинаков (`[]`), хранится состояние чеклиста; в коде следует формулировке DDL (канон сущности БД) — «состояние чеклиста онбординга С5».
- `*_json` в БД — строки; наружу отдаются как вложенные JSON-значения (после applyPatch в БД только валидный JSON, включая DEFAULT-строки миграции).

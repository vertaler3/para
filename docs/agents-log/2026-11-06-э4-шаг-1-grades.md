Коммит «Э4: шаг 1 — GradesService: GET /v1/grades и /grades/summary»».

## Что сделано

- `src/services/GradesService.{h,cpp}` — вся SQL параметрами (AGENTS.md §5.5, 02 §6.4), обе выборки идут по `idx_grades_user` (user_id, discipline_id) — проверено `EXPLAIN QUERY PLAN` на БД из реальных миграций+фикстур: обе — `SEARCH g USING INDEX idx_grades_user (user_id=?)`; JOIN `disciplines` даёт карточкам `code`/`discipline`. Формы ответов 02 §5.2:
  - `GET /v1/grades` → `{"grades":[…]}` — свои записи (user_id из сессии): `id, discipline_id, code, discipline, control_type (из строки grades), component, score, max_score, attempt, comment (null если нет), graded_at`; порядок — по дисциплине, внутри по `graded_at`.
  - `GET /v1/grades/summary` → `{"average": int|null, "disciplines":[…]}` — агрегат по дисциплинам: `discipline_id, code, discipline, control_type (из disciplines), score_sum, max_sum, percent, missing`.
  - **Семантика сводки** — демо-арифметика 05 §3 Э4 / 03 §4.9.3 («30+30+18=78 при пороге 82 — до допуска не хватает 4»): порог допуска дисциплины = Σ `max_score` её компонентов с оценками (у d1 в фикстурах 30+30+22=82); прогресс `percent` = 100·Σscore/Σmax; «что осталось» `missing` = max(0, Σmax−Σscore) — у d1 это 4; строки дисциплины суммируются как есть — пересдача (attempt≥2) по 05 §3 Э4 показывается отдельной строкой списка, правило пересчёта итога после пересдачи — ветка этой строки, не шага 1. Средний балл `average` — взвешенный процент по всем дисциплинам с оценками (Σscore/Σmax·100, округление до целого).
  - **average/percent — целые JSON-числа** (сознательное решение шага): jsoncpp (drogon v1.9.14) сериализует дробные двойники полной репрезентацией — проба в образе: `83.2` → `"83.200000000000003"`, `95.1` → `"95.099999999999994"`, целые — детерминированно (`83`, `100.0`); подписи прогресс-баров 03 §2.8 («78/100», пороги цвета ≥60/40–59/<40) — целые проценты. Дробный средний балл шкалы 0–5 из вайрфрейма 03 §4.4 («4.3») к баллам фикстур (0–100 за дисциплину) не применяется нигде в 02 — если FE-дорожке понадобится дробный, это отдельное решение с записью в docs/decisions.md.
  - Оценок нет (Аня — «оценки появятся после первой аттестации», 03 §4.4; staff) — 200 с `average=null` и пустым `disciplines`: сериализуется как `{"average":null,"disciplines":[]}` — «пустое» состояние сводки; `null`, а не 0 — FE отличает «нет данных» от «средний ноль».
  - Ошибка БД — fail-closed `ok=false` → 500 контроллером (не «пустая успеваемость»); колбэк копируется в обе ветки цепочки `>>` (урок Э2 шаг 1 — двойной move → bad_function_call на error-пути).
- `src/controllers/GradesCtrl.{h,cpp}` — тонкий (два метода, SQL нет): user_id только из атрибута сессии LoginFilter; `Result` → 200 JSON либо 500 `{"error":{"code":"internal",…}}` через общий `api::errorResponse` (02 §5.1). Оба маршрута в METHOD_LIST под `"LoginFilter"` (публичные префиксы фильтра /v1/grades не включают — без cookie 401 от фильтра). path-id нет — OwnershipGuard не применим; **GET /v1/grades/{id} (владение через guard, 02 §5.2) и GET /v1/exams — следующие шаги Э4, в этом шаге не заложены**. `static/` и `views/` не тронуты.
- `tests/unit/grades_service_test.cpp` — 5 тест-кейсов на временной SQLite (схема — колонки disciplines/grades миграции 0002 без FK + индекс §4.2; данные копируют оценки фикстур дословно: user 3 — ids 1–10, включая неуд «История МЭО» id 10 с комментарием; дополнение помечено — id 99 пользователя 9): пустой список + пустая сводка (average=null, disciplines=[]) у Ани и у пользователя без строк; список — свои 10 строк фикстур, поля строки, comment null/не null, изоляция (id 99 не в списке Марка, у user 9 только его строка); сводка Марка — d1 78/82/percent 95/missing 4, d8 60/60/100/0, d3 25/60/42/35, average=83 (Σ293/Σ352 — сверено sqlite по фикстурам); сводка по одной строке (user 9) — average=100, missing=0; ошибка БД (пустая схема) — ok=false у обоих методов.
- `CMakeLists.txt` — GradesCtrl.cpp в `para`; GradesService.cpp в `para` и `para-tests`; тест в `para-tests`.

## Расхождения постановки с фикстурами (проверено sqlite по реальным миграциям+фикстурам, не по памяти)

1. **«У Марка 8 записей» — в `sql/fixtures.sql` их 10**: `SELECT COUNT(*) FROM grades WHERE user_id=3` → 10 (ids 1–10; 9 строк октября + неуд «История МЭО» id 10 от 24.06 с комментарием «Порог не достигнут; пересдача 18 ноября»). Тесты и E2E сверены с фактическими фикстурами (10), в журнале шага это отмечено; формулировку AGENTS.md/фикстур не правил (вне шага).
2. **«порог допуска 78/82»** — в DDL нет колонки порога (`disciplines`: id/code/title/control_type); порог 82 в 05 §3 Э4 и 03 §4.9.3 совпадает с Σ max_score компонентов дисциплины 1 (30+30+22) — сводка считает порог из данных, что воспроизводит каноничную демо-арифметику без новых колонок/фикстур.

## Ошибки ИИ, пойманные и исправленные в ходе

1. **Позиционное обращение `grades[0]` в тесте**: ожидал в `[0]` строку id 1, но `ORDER BY d.title` ставит первым «Деловой английский» (id 8, «Д» < «М») — 9 проверок упали (`first["id"] == 1` → 8). Сервис корректен; тест переписан на поиск строки по id 1 (паттерн цикла по массиву), позиционные допущения убраны.
2. **Двойное применение миграций в локальной проверке** (перенёс < на два файла, потом цикл) — «table already exists»; переделано на чистый прогон 0001–0005 + fixtures без ошибок, факты пересняты.
3. **Несоответствие образа**: базовый `drogonframework/drogon:v1.9.14` не содержит `libargon2-dev` и `ninja` (их ставит наш Dockerfile в build-стадии) — в одноразовом контейнере ставился apt-пакет `libargon2-dev`, сборка на Unix Makefiles; зафиксировано, чтобы следующий шаг не наступил на те же грабли.

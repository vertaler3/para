## Что сделано

- `src/services/OwnershipGuard.{h,cpp}` — единственная функция `check()` (02 §6.3: «одна функция, проверяющая владение до любой отдачи данных»). Выбран вариант **fetch-and-compare из (sessionUserId, таблица, id объекта)**: §6.3 определяет guard для path-id объектов (`applications/{id}`, `grades/{id}`, `notifications/{id}`) — у контроллера на входе только id из URL, поэтому guard сам достаёт `user_id` («SELECT user_id FROM … WHERE id = $1», id — параметром) и различает NotFound (строки нет → 404) и Forbidden (строка чужая → 403); вариант (sessionUserId, targetUserId) требует предварительной загрузки объекта и 404 не даёт. Выбор описан в заголовке. Белый список таблиц — `enum class Table { Applications, Grades, Notifications }`; имя таблицы разворачивается в фиксированный SQL-литерал switch'ом (конкатенации нет, 02 §6.4). Добавлен четвёртый вердикт `Error` — ошибка БД, fail-closed (не превращается в разрешение; контроллер отвечает 500). Стиль асинхронных колбэков — как `UserService`.
- **Правило код-ревью зафиксировано в шапке `OwnershipGuard.h`:** «Контроллер с path-id обязан вызвать OwnershipGuard» — все новые path-id эндпоинты идут через guard (Э4/Э5+); маппинг Verdict→HTTP (Own → продолжить, NotFound → 404, Forbidden → 403, Error → 500) — в контроллере.
- `tests/unit/ownership_guard_test.cpp` — 4 тест-кейса на временной SQLite через настоящий `DbClient` (паттерн TempDir из теста миграций): своё → Own (все три таблицы белого списка), чужое → Forbidden (три таблицы, в обе стороны), несуществующее → NotFound (не маскируется под Forbidden), ошибка БД → Error (fail-closed, БД без таблиц). Фикстуры — напрямую sqlite3 API до открытия клиента; каждый вызов guard'а синхронизируется promise/future (колбэки DrogonDbClient — с внутреннего потока).
- `CMakeLists.txt` — `OwnershipGuard.cpp` в целях `para` и `para-tests`, тест-файл в `para-tests`.

## Ошибки/уточнения ИИ, учтённые в ходе

- **`const char*` в `DbClient::operator<<` неоднозначен** (перегрузки `string`, `string&&`, `string_view`; специальная перегрузка для литералов-массивов на decayed-указатель не срабатывает) — `sqlFor()` возвращает `std::string_view`, точное попадание в `operator<<(const string_view&)`. Поймано компиляцией (gcc 11, контейнер drogon v1.9.14).
- **Двойной `cb = std::move(cb)` в цепочке `>>` — crash на error-пути.** Первая лямбда (result) забирала колбэк move'ом, вторая (exception) получала moved-from (гарантированно пустой) `std::function` → `std::bad_function_call` в event loop при первом же сбое БД (terminate, SIGABRT). Юнит-тест Error-ветки поймал сразу; локализация — по логу «log-строка печатается, затем bad_function_call на loop-потоке» + три эмпирических репро (одиночный клиент / 4 цикла / raw-sqlite3-прелюдия) отсекли гипотезы teardown-гонки и MULTITHREAD, после чего причина найдена статически по исходникам Drogon 1.9.14 (SqlBinder.h `operator>>`, Sqlite3Connection.cc `onError`). Исправлено: колбэк копируется в обе ветки (стреляет ровно одна).
- **Латентный баг того же рода в Э1 (вне шага, не правил):** `src/services/UserService.cpp` — `findByLogin` (строки 15–33) и `loadProfile` (строки 41–66) используют ту же пару `[cb = std::move(cb)]` в result- и exception-лямбдах; при ошибке БД будет тот же `bad_function_call`. До сих пор не стреляло — error-путь запросов не покрывался тестами. Рекомендация: починить тем же способом (копия в обе ветки) при первой правке UserService (например, в шаге настроек уведомлений Э2) или на Э8.
- Ninja в чистом образе нет (его ставит Dockerfile) и компилятора на PATH под именем `g++`/`clang++` нет — только `g++-11`; проверочный прогон — генератором Unix Makefiles (как в Э1).
- `FATAL SQLITE_CONFIG_MULTITHREAD is not supported!` в логе тестов — известная находка Э1 (medium, без mustFix): `std::call_once` + `sqlite3_config` после инициализации libsqlite3 raw-тестами миграций; только лог, соединение открывается.

## Что сделано по шагам

1. **Шаг 4 — миграционный раннер** (коммит **`f85194c`** «Э1: шаг 4 — миграционный раннер (schema_migrations, транзакции, --seed)», 8 файлов / 763 insertions): `src/services/MigrationRunner.{h,cpp}` — сам создаёт `schema_migrations(version TEXT PK, applied_at ISO 8601 UTC)`; применяет `sql/migrations/NNNN_*.sql` по возрастанию номера; каждый файл — `BEGIN IMMEDIATE` → тело → параметризованный `INSERT` версии → `COMMIT`, при ошибке `ROLLBACK` + `MigrationError`; `PRAGMA user_version` обновляется **внутри той же транзакции** (дублёр не отстаёт от `schema_migrations` и после отката упавшего файла); fail fast в `main.cpp` — ошибка миграций логируется и процесс выходит с кодом 1 до поднятия роутов. Режим `--seed` применяет `sql/fixtures.sql` той же транзакционной схемой; идемпотентность — маркер `'fixtures'` в `schema_migrations`; отсутствие файла фикстур при `--seed` — WARN и пропуск. `config.json`: `db_clients` (sqlite3, `/opt/para/data/para.db`, WAL + `synchronous=NORMAL` через `initialization_queries`) и `custom_config.db_path` — путь записан дважды осознанно, инвариант-комментарий в самом файле (`db_clients` публично не читается до `app().run()`). Юнит-тесты `tests/unit/migration_runner_test.cpp`: идемпотентность, `user_version`, WAL, откат по ошибке, `--seed` без файла, фильтрация/сортировка каталога. Решение — **Р-5** (транспорт раннера — синхронная libsqlite3, не DbClient: пул DbClient создаётся только внутри `run()`, вариант через DbClient применял бы миграции уже после открытия порта).
2. **Шаг 5 — миграции 0001–0005** (коммит **`b0e19c6`**): DDL по 02 §4.1 + все 9 индексов §4.2; 21 таблица. Ревьюером побайтово сверены с 02 §4.1 (механический diff; расхождение — только `\n` в конце).

## Ошибки и правки (итог по сессии; детали — в пограничных журналах шагов)

1. **`user_version` отставал после отката упавшего файла** (шаг 4) — первая версия раннера ставил PRAGMA после цикла; поймал собственный юнит-тест; исправлено установкой внутри той же транзакции, что и INSERT версии.
2. **CLI argon2 не принимает память 19456 через `-m`** (шаг 6): в apt-пакете 20190702 флаг `-m` — log2(КиБ), «bad numeric input»; память в КиБ задаёт `-k`, encoded-строка каноническая. У CLI нет verify-режима — верификация мини-C на `argon2id_verify()`. Зафиксировано в Р-6.
3. **Шаг 7, сборка:** `drogon::orm::DbClientPtr/Result` требуют собственной квалификации namespace; `drogon_create_views` нельзя до `add_executable`; скомпилированный `.csp` — `DrTemplate`, роут сам не создаёт (404 на `/login`) → тонкий GET в AuthCtrl; `registerFilter` для `HttpFilter<T>` запрещён static_assert'ом; тест лимитера ловил ошибку отсчёта в самом тесте — исправлен тест, не реализация.
4. **Гейт, раунд 0 — красный:** `login → 401 invalid_credentials`, в БД `users = 0`. Причина: ENTRYPOINT запускал бинарь **без `--seed`** (примечание «флаг добавим на шаге 6» из Р-5 не исполнилось при закрытии шага 6); смок шага 7 прогонял бинарь с `--seed` вручную и контур образа не покрывал. Исправлено в `0222161` (Р-8); после фикса гейт зелёный.
5. **Ревью, 2 mustFix:** plaintext демо-пароля в `docs/decisions.md:78` (вход им прошёл живьём — нарушение §5.2/02 §6.2) и SQL в `AuthCtrl` (нарушение §5.5/02 §6.4) — оба применены в `d484eff`.
6. **Ревью, medium/low (без mustFix, не правились):** `foreign_keys=0` во всех соединениях, FATAL MULTITHREAD в каждом логе старта, форма → 400, timing-оракул входа, неполное зеркало лимитера в `users.failed_attempts`, отсутствие CSP/nosniff-заголовков — зафиксированы для плана Э8.

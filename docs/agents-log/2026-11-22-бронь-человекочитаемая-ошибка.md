# 22.11.2026 — бронь: человекочитаемая ошибка вместо API-валидации

Инцидент (скрин владельца 11:06): при попытке забронировать аудиторию,
когда время уже прошло интервал, сервер корректно отвергает бронь (фикс
«create отвергает прошедшие интервалы», 5cd5b8a), но пользователь видит
сырой текст валидации API: «starts_at/ends_at — ожидается ISO 8601 UTC
(YYYY-MM-DDTHH:MM:SSZ), интервал в будущем, ends_at позже starts_at».

## Причина (FE, static/js/app.js)

`bookSlot()` при не-201 знает только коды `slot_taken`/`not_found`; всё
остальное уходит в `serverText()`, который для русского языка возвращает
`error.message` как есть — валидационный текст `bad_request` и попадал в
баннер. Сценарий: сетка слотов открыта, выбранный слот «уходит в
прошлое» (страница не перезагружалась) → кликабельный устаревший слот →
POST → 400.

## Фикс A+B (по согласованию с владельцем; BE не тронут)

- **A (превентивно)**: в `bookSlot()` ДО запроса — если `ends_at` слота
  уже прошёл (`Date.parse(slot.ends_at) <= Date.now()`): предупреждение
  `rooms.slotPast` («Это время уже прошло — выберите слот позже»),
  `resetSelection()` и тихий ре-фетч сетки; сервер не дёргается вовсе.
- **B (страховка)**: явная ветка `bad_request` в `bookSlot()` и в отмене
  брони (диалог) — студенту словарная строка (`rooms.badBooking` /
  `rooms.badCancel`), исходное сообщение сервера — `console.warn`
  разработчику. Утечка сырых текстов в UI закрыта для любых будущих
  формулировок валидации.
- Ключи i18n ×3 языка (ru/en/zh, `src/models/i18n.h`, таблицы
  отсортированы — вставлены по алфавиту): `rooms.badBooking`,
  `rooms.badCancel`, `rooms.slotPast`.

  100% (i18n-тест гоняет полный keyset 3×N — согласованность ключей
  подтверждена).
- Живой e2e сценария владельца (контур `up -d --build`, 09:36 UTC,

  `bad_request` → баннер **«Не получилось забронировать: проверьте дату
  и время слота»** — без ISO/английского (скрин
  `gui-audit-2026-11-19/63-booking-human-error.png`, вне репо). Это

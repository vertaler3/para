## Решения

1. **Семантика окна days=7 — фильтр по starts_at, не по changed_at.** Сверено с кодом: `ScheduleService::recentChanges` (`src/services/ScheduleService.cpp:230-237`) — окно [today-(days-1), today+1) по starts_at, комментарий «Изменение будущей даты показывается в день её наступления». Поэтому критерий исполнения: в каждой календарной неделе 09–30.11 ≥1 moved/cancelled по starts_at и разрыв между соседними изменёнными датами ≤7 дней (04–05.11 → 11–12.11 → 17.11 → 20.11 → 27.11 → 30.11; максимальный разрыв 7 дней — 20.11→27.11, при ширине окна 8 календарных дней окно непусто всегда). Проверено SQL-перебором всех 22 дней 09–30.11 — пустых окон 0.
2. **Новые переносы — БЕЗ schedule-уведомлений.** Совместимость постановки: «уведомления пяти основных — как есть, кроме НОВЫХ дедлайнов». Лента изменений (С3) и экран расписания читают их по status/prev_*; push-сценарий переноса покрыт существующими уведомлениями 1–6.
3. **Дедлайн 5 — якорь напоминания Ани — due 11.11 21:00** (в ходе сессии сдвинут с 10.11 21:00: часы пересекли полночь UTC — при 10.11 дедлайн был бы «вечером сегодня», при 11.11 он остаётся активным на демо-времени 11–13.11; напоминание Ани «уже отправлено» 10.11 21:00 с активного дедлайна).
4. **body уведомлений — читаемая дата в самих данных.** В коде `ReminderService` пишет body = «Срок: »+ISO / «Ваше напоминание — срок: »+ISO (`src/services/ReminderService.cpp:125,213`), человекочитаемый формат добавлен на FE (коммит `4fe7362`, static/js/app.js). Постановка требует читаемую дату прямо в body фикстур — сознательное расхождение данных с текущим форматом body кода зафиксировано здесь; формат даты «11 ноября 21:00» + маркер «(вымышленный)» — по примерам постановки.
5. **Расхождение постановки с фактом:** задание называет «existing notifications id 1–18», в свежем сидировании фактический максимум — **6** (`sql/fixtures.sql:144-150`, после Э1; diapason 7–18 — числа из живых БД гейтов, в фикстурах их нет). Новые уведомления — ids 7–8 явными id, продолжают нумерацию файла; на свежей БД коллизий нет.
6. **deadline_reminders — на групповые дедлайны СВОИХ групп** (правило POST /v1/deadlines/{id}/remind, docs/02 §5.2: групповые — только своей группы): Аня — дедлайн группы 1, Марк — дедлайн группы 2.

## Ошибки (по ходу)

- **Верификация argon2:** `openssl base64 -d -A` молча терял 2 байта на непаддированном base64url-теге (43 символа вместо 44) — ложные «VERIFY FAIL». Исправлено: паддинг `t += '='*(-len(t)%4)` + декодирование python3; сверка с сырым тегом `argon2` (строка `Hash:`) — 26/26 ok. Пароль в команды/вывод не попадал (создавался и жил только в переменной контейнера).

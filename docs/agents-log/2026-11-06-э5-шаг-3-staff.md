## Что сделано

- **`src/filters/StaffFilter.{h,cpp}`** — RBAC-фильтр (02 §6.3: «StaffFilter на /v1/staff/*; студент, вызвавший staff-эндпоинт, получает 403»): роль — только из атрибута сессии ("session", кладёт LoginFilter; в БД её тянет SessionService::findValid — JOIN users, users.role CHECK 'student'|'staff' миграция 0001); параметр роли от клиента не принимается. Не staff → 403 `{"error":{"code":"forbidden","message":"Доступ только для сотрудников"}}` (02 §5.1). Отсутствие атрибута (роут без LoginFilter — ошибка конфигурации) — fail-closed: `Attributes::get<T>` при отсутствии ключа возвращает `T()` (проверено по заголовкам v1.9.14, drogon/Attribute.h:42–44) → пустая роль → 403. Вешается после LoginFilter: `"LoginFilter", "StaffFilter"` в METHOD_LIST; SQL не выполняет. Регистрация — тот же механизм HttpFilter<T>, что у LoginFilter (main.cpp).
- **`src/models/Applications.h`** — `applicationStatusTitle(status)` — 9 человекочитаемых меток статусов (01 §4.4 таймлайн «подана → принята → в работе → готова → выдана», С7.5 «Требуется уточнение») для уведомлений и бейджей; constexpr, словарь = CHECK DDL.
- **`src/services/AppWorkflow.{h,cpp}`** — `apply()` получил опциональный хук `AfterEventTx(tx, fail)` (default nullptr — прежние вызовы не изменились): выполняется В ТОЙ ЖЕ транзакции после записи события и до коммита (05 §3 Э5 п.3: «в одной транзакции: UPDATE + событие + INSERT в notifications»); tx передаётся shared_ptr (хук захватывает в свои колбэки — держит транзакцию до завершения последствий), `fail()` = fire(Error) + rollback всей транзакции (статус+событие+последствия атомарны); fire защищён once — commit-callback не задублирует.
- **`src/services/ApplicationsService.{h,cpp}`**:
  - `queue(db, QueueFilters)` — GET /v1/staff/applications. Одна параметризованная SQL с «filters-or-empty» (`WHERE ($1 = '' OR a.status = $1) AND ($2 = '' OR a.type = $2) AND ($3 = '' OR overdue-предикат)`) — без конкатенации строк (02 §6.4), порядок $N в тексте = порядку биндинга (урок шага 2). overdue («горит», 03 §4.8 — бейдж «при приближении срока») = обновление старше 3 дней в активном статусе (submitted/accepted/in_progress/need_info; С2.4 «обычно до 3 рабочих дней» — консервативно в календарных); draft и терминальные не «горят»; колонка overdue возвращается и без фильтра. Сортировка `a.updated_at ASC, a.id ASC` (очередь: дольше ждут — выше; idx_applications_queue). Владение НЕ проверяется (staff видит все — постановка); JOIN profiles/groups — LEFT (заявка без профиля не пропадает), в строке `owner{fio,group}` (С8.3) + `overdue`.
  - `staffChangeStatus(db, applicationId, toStatus, comment, staffUserId)` — POST .../status: `AppWorkflow::apply` (матрица шага 1) + хук уведомления: внутри транзакции SELECT владельца/типа → `INSERT INTO notifications (user_id, type, title, body, deep_link) VALUES ($1,'application',$2,$3,$4)`; title — «<type_title>: <метка статуса>» из констант models, body — comment (rejected «с причиной» — 05 §3 Э5), deep_link — `/applications/{id}` (4.5: тап → таймлайн). OwnershipGuard сознательно НЕ вызывается (staff видит все — постановка шага; guard — для student-owned объектов); несуществующий id → NotFound → 404. Applied → SELECT карточки по PK → Ok.
- **`src/controllers/StaffCtrl.{h,cpp}`** — тонкий: GET/POST под `"LoginFilter", "StaffFilter"`; валидация query (status ∈ словарь, type ∈ каталог, overdue ∈ {'', '1'} → иначе 400) и тела (to_status — строка ∈ словарь, иначе 400 — ошибка тела, не перехода; comment — опциональная строка); маппинг: Ok → 200 карточка, InvalidTransition → 409 `invalid_status_transition` «Недопустимый переход статуса заявки», NotFound → 404, Error → 500. htmx-фрагмент по HX-Request (02 §3.2 поток 2) — при интеграции FE (views/ не трогаем; FE Э5 не начиналась), помечено в шапке контроллера. StaffCtrl — точка роста Э6 (переносы, объявления).
- **`tests/unit/applications_service_test.cpp`** — фикстура расширена (notifications с CHECK type, profiles/groups из 0001; seedApp — опциональные type/updated_at), +2 кейса:
  - очередь: без фильтров — все 4 seeded заявки по updated_at ASC (связи по id), owner fio/group, overdue-флаги (старая активная true; draft/issued/свежая false); ?status; ?type; overdue=1 (только старая активная); overdue+status (пусто). Старые/свежие updated_at — фиксированные '2026-01-01'/'2099-01-01' — детерминированно к времени прогона.
  - смена статуса staff-ом: in_progress→ready → Ok + статус + событие (author=staff) + уведомление АВТОРУ заявки (user_id=4, type='application', «Академическая справка: Готова», deep_link, read_at NULL); rejected с комментарием (из in_progress — из ready только issued!) → body = причина, уведомление автору той заявки; недопустимый rejected→in_progress → InvalidTransition и НИ одного уведомления/события (полный откат); 999999 → NotFound; пустая схема → Error.

## Ошибки ИИ, пойманные и исправленные в ходе

1. **Тот же класс ошибки захвата, что в шаге 2:** `newTransactionAsync`-лямбда вложена в SELECT-колбэк статуса — `afterEvent` не был в его capture-списке («‘afterEvent’ is not captured», каскад на все вложенные лямбды); аналогично в хуке уведомления не захватывался `fail`. Добавлены захваты.
2. **Ошибка ожидания в моём тесте, не в коде:** пытался сделать rejected из ready — по матрице 05 §3 Э5 из ready только issued; rejected-ветка переведена на заявку в in_progress (для rejected есть submitted/accepted/in_progress/need_info).
3. **Двойной rollback в хуке:** ветка «заявка исчезла» звала tx->rollback() И fail() (который уже rollback+fire) — убран прямой rollback.
4. **-Wmissing-field-initializers** на designated-initializers `{.status=…}` (GCC 11 даже для C++20) — явное заполнение QueueFilters полями.
5. Правка-ошибка редактирования: вставка staff-блока съела сигнатуру `catalog()` и закрыла namespace в середине файла — замечено grep'ом по структуре (namespace открыт/закрыт, наличие сигнатур), восстановлено до сборки.
